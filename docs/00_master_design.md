## 1. 주제와 문제
- **주제:** 취소해도 남는 공유 차 키 — 오프라인 차량을 위한 차량 측 사용 제한 모듈
- **한 줄 요약:** 카셰어링·렌터카 이용이 끝난 뒤 남는 디지털 차 키를, 서버와 연결이 끊긴 차량이 스스로 제한·만료시키는 모듈
- **핵심 기여 (11/4 결정):** 서버와 통신이 끊긴 차량이 스스로 공유 키 사용을 제한하는 모듈을 실제 보드로 구현하고, 여러 제한 방식을 같은 조건에서 비교해, 차를 공유할 때 어떤 제한 방식을 고르는 것이 좋은지 판단할 근거를 제공한다.
  - 포스터용 짧은 판: "끊긴 차도 스스로 지키는 공유 키 — 제한 방식을 같은 조건에서 비교해 '어떻게 공유할지' 선택을 돕는다."
  - 방식 C(오프라인 횟수)·B(기간)는 기존 방식이며 비교 대상이다. 중간발표는 A·C 실물 비교, 최종은 A~D(+E) 비교(T06)로 상황별 추천. 비교 결과가 나오기 전에는 "판단할 근거를 제공한다/도울 수 있다"로 쓰고 "도움을 줬다"로 쓰지 않는다
- **연구 초점과 평가 축 (11/5 결정, 지도교수 자료 §2.4 "키 공유·폐기"를 따른다):** 차량이 오프라인이면 방금 서버에서 한 폐기를 즉시 알 수 없다는 구조적 한계를 인정하고, "즉시 폐기"가 아니라 아래 네 가지를 **방식별로 정량화**해 비교한다. 지금까지의 "6회 중 몇 회 허용"은 ①의 한 칸이다.
  | 축 | 뜻 | 지금 상태 |
  |---|---|---|
  | ① 폐기 후 최대 사용 | 취소된 키로 오프라인에서 더 쓸 수 있는 **횟수·시간** | 횟수(C 4회)만 실물 1회. 시간 축은 RTC 뒤(B·D) |
  | ② 정상 이용자 오프라인 허용 | 취소 안 된 이용자가 오프라인에서 쓸 수 있는 횟수·시간 (= 제한의 비용) | 미측정. C는 정상 이용자도 4회 뒤 05 |
  | ③ 갱신 통신량·전력 | SYNC 주기·크기, 전력 | 미측정(계산값부터) |
  | ④ 재부팅·시계 견고성 | 재부팅·재등록·시계 되돌림으로 상한이 무너지지 않는가 | **재부팅 시 초기화됨(§6 7-1, 알려진 구멍)**, 시계는 RTC 뒤 |
  - 같은 자료의 근접성 검증(§2.1~2.3 릴레이·UWB·전환), 계정·클라우드(§2.5), VSOC 탐지(§2.6)는 **범위 밖**이다. 휴대폰↔차 근거리 구간은 정당한 근접으로 가정한다
  - 방식 F(AI 보류)·E+는 §2.6 탐지 쪽에 가까워 **최종 범위에서 "확장 가능성"으로 내린다**(§7). 시간이 남으면 되살린다
- **11/5 지도교수 면담 결과 (녹취 기준):** 주제는 좋고 더 키울 수 있다("졸업작품으로만 묻기 아깝다", 쏘카 등 카셰어링 업체 세일즈·특허·기술 이전까지 가능). **지금 시험은 그대로 진행**하되, 아래 세 숙제의 답을 누군가 준비할 것. 시연은 Pi 연결 문제로 못 보여 드림 → 다음 면담 때
  1. **오프라인에서 생길 수 있는 문제를 구체화** — "더 오래 쓴다"에서 끝내지 말고 도난·해외 반출·금전 이득 등 **더 심각한 결과**로 이어지는지. 특히 A(보안 없음)를 더 분석해 필요성으로 연결 (§1.2)
  2. **차가 스스로 오프라인임을 어떻게 아는가** — B·C 모두 시작점이 "오프라인 판정"인데 답이 없었음. 하트비트 + ACK(왕복)로 끊김을 인식하는 방식, 쏘카가 실제로 어떻게 하는지 조사. 우선은 "감지했다고 가정"하고 병렬 진행 가능 (§6 10)
  3. **현실 조건 반영** — 쏘카처럼 시간을 미리 결제하는 경우 **결제한 기간 안의 오프라인은 문제가 아닐 수 있다.** 지금 C는 돈을 낸 정상 이용자도 잠근다. 대여 기간을 고려한 최종 알고리즘 하나는 있어야 함 (§7 현실 조건)
  4. 결과 제시는 **방식 1(공격 시나리오별 방어 여부)을 더 깊게** — 잘 알려진 공격이 아니라 **공유차 특성(이용자가 계속 바뀜, 이용자 사이 공백, 그사이 오프라인)**을 파고드는 공격을 찾아 방식별로 평가 (§2.1). 방식 2(시간 대비 피해량)는 보조

### 1.2 오프라인에서 생길 수 있는 문제 — 나쁜 마음을 먹으면 어디까지 가나 (면담 숙제 1, 11/5 저녁 보강)
**핵심 통찰: 오프라인은 "우연히 생기는 상태"가 아니라 공격자가 만들 수 있는 상태다.** 지하주차장으로 옮기기, 통신 모듈 퓨즈·안테나 분리, 전파 차단 가방·재머, 서버 장애 시간대 노리기, 차가 스스로 통신을 끄는 장시간 주차(블루링크 48~336h) 기다리기. 공격자가 오프라인 시점을 고를 수 있으므로 "오프라인은 드물다"는 가정은 쓰지 않는다.

**공격자 (누가):** ① 정당하게 빌렸다가 취소된 전 이용자 ② 남의 명의로 빌린 사람(실제 사례, 2017 광주 무면허 17세·명의 도용 반복) ③ 전 이용자가 키를 넘긴 공범 ④ 발레·대리 같은 잠깐 맡은 사람

| 단계 | 공격 사슬 (A, 보안 없음) | 피해 | 지금 설계(C·D)의 효과 |
|---|---|---|---|
| L1 무단 사용 | 취소된 키로 문 열고 시동 | 요금 미납·사고 책임 혼선 | 횟수·기간으로 상한 |
| L2 절도·사생활 | 반납 후 공백에 들어가 다음 이용자 짐 절도, 차 안 설치물(카메라·추적기) | 재산·사생활 | 상한 (횟수 소진 전엔 허용) |
| L3 위장 운행 | 명의 도용 계정 + 취소 키로 **무면허·뺑소니** (실제 사례) | 인명 | 상한 |
| L4 추적 회피 운행 | **시동 1회 뒤 끄지 않고 운행** + 통신 차단 유지 → 서버는 위치도 취소 반영도 못 함 | 장거리 무단 운행·범죄 이용 | **못 막음** (횟수는 시동 횟수, 운행 시간 제한 없음 = S3) |
| L5 도난·반출 | L4 상태로 컨테이너·항구 이동, **해외 반출·부품 판매**. 테슬라 렌터카 사례: 반납 후 인증이 제거됐는데도 앱으로 잠금 해제·시동, GPS 끄려 시도, 충전 기록으로 추적·체포 | 차량 가치 전체 | **못 막음** (L4와 같음) + 재부팅 재등록(S4)으로 횟수 복구 |
| L6 확산 | 키 정보 복사로 여러 명·여러 차 동시 | 조직 범죄 | 키별 상한만 |

- **결론:** A는 L1~L6 전부 열려 있다. 지금 C·D는 L1~L3를 상한으로 줄이지만, **치명적 단계(L4·L5)는 "시동 뒤 운행 시간/거리 제한"과 "재부팅 뒤 횟수 보존"이 있어야 막힌다.** 이것이 최종 알고리즘(§7 D-현실)에 들어가야 할 두 조건이다
- 실제 사례: 테슬라 모델3 렌터카 도난([CarAdvice](https://www.caradvice.com.au/683106/tesla-model-3-phone-key/), 반납 후 인증 해제됐음에도 재접근·시동·GPS 차단 시도), 카셰어링 명의 도용 무면허 뺑소니([뉴스토마토 2017-02-14](https://newstomato.com/ReadNews.aspx?no=731336)), Car2Go 시카고 100대 도난(앱 계정 악용, [VICE](https://vice.com/en/article/thieves-steal-100-car2go-cars-chicago)), 그린카 2022 서버 마비로 스마트키 불가([비즈한국](https://www.bizhankook.com/bk/article/23578))
- 쏘카: 블루투스 스마트키, 시간제 예약(30분·1시간 단위). 조기 반납·연장 정산과 차량 오프라인 판정 방식은 공개 자료에서 확인 못 함(김채희 추가 조사)
- 포스터 ② "문제" 장: L1→L5 사슬 그림 + 테슬라 사례 한 줄

## 2. 사건 유형 (교수님 피드백 반영)
### 2.1 공유차 특화 공격 시나리오 (면담 숙제 4, 초안 — 방어 여부는 설계상 예상, 측정 아님)
| # | 시나리오 (공유차 특성 이용) | A | B 기간 | C 횟수 | D | 비고 |
|---|---|---|---|---|---|---|
| S1 | 반납 직전 차를 **지하로 옮겨 오프라인을 만든 뒤** 반납·취소 → 다시 와서 사용 | 허용 | 기간 안 허용 | 4회 | 둘 다 | 기본 시나리오 |
| S2 | 반납 후 **다음 이용자가 오기 전 공백**에 재진입(물품 절도) | 허용 | 기간 안 허용 | 4회 | 둘 다 | 공백이 길수록 위험 |
| S3 | **시동 1회로 계속 운행** (끄지 않음) + 통신 차단 유지 | 허용 | 기간 뒤에도 운행 중이면? | **1회 소모 후 무제한** | 같음 | **설계 구멍 → L4·L5 도난·반출**: 시동 뒤 운행 시간 제한 없음 |
| S4 | 4회 소진 뒤 **배터리 단자 분리로 재부팅** → KEY 재등록 | — | ? | **횟수 복구(구멍)** | 같음 | §6 7-1, 플래시 저장으로 막음 |
| S5 | 다음 이용자 이용 중 **이전 이용자가 문을 엶** | 허용 | 기간 안 허용 | 4회 | 둘 다 | 반납(09) 처리된 키는 거부 |
| S6 | 키 정보를 **공범에게 복사** | 허용 | 기간 안 | 4회(공유) | 둘 다 | 막지 못함, 상한만 |
| S7 | B에서 **RTC 시계 되돌림** | — | **취약** | 영향 없음 | 취약 | 마지막 시각 저장으로 대응 |
| S8 | **가짜 서버**로 "온라인인 척" 횟수 복구 | — | — | 거부(서명·nonce) | 거부 | 이미 막음 |
| S9 | 정상 **대여 기간 중 지하주차장** (공격 아님, 정상 이용자) | 허용 | 허용 | **4회 뒤 잠김 = 오탐** | 기간 안이면? | 교수님 지적: 결제한 기간 안은 막으면 안 됨 |
- S3·S4·S9가 지금 설계의 약점이다. S3는 "시동 뒤 운행 시간/거리 제한", S4는 플래시 저장, S9는 대여 기간을 고려한 알고리즘(§7)으로 풀어야 한다
- 이 표를 현실화(사례·조건)하고 방식별 방어를 평가하는 것이 최종 결과의 중심(방식 1), 시간 대비 피해량(방식 2)은 보조
| # | 사건 | 대처 |
|---|---|---|
| ① | 일찍 반납 | 반납 버튼 → 차량 내부 즉시 무효화 |
| ② | 반납 처리 안 됨 | 시동 off + 잠금 + N분 후 자동 만료 (11/16 이후) |
| ③ | 오프라인 중 취소 | 오프라인 횟수 제한 (방식 C) |
| ④ | 키 유출·재전송 | HMAC + 1회용 nonce |
| ⑤ | 늦은 반납 | 만료 후 새 시동 거부 (방식 B/D) |
| ⑥ | 차량 판매 | 키 자동 삭제 안 됨 → 소유권 이전 시 전체 무효화 (확장 과제) |

## 3. 전체 구조
```
[노트북] server.py (발급·취소·버전) + app.py (주인/받는 사람 앱 대신)
    │ TCP 9000 (동기화)          │ TCP 9100 (앱 요청)
    ▼                            ▼
[Raspberry Pi] pi_relay.py : 줄을 그대로 전달만 함 (판단 없음)
    │ USB (ST-LINK 가상 COM, 115200 8N1)
    ▼
[NUCLEO-F429ZI] sharekey.c : 인증·판단 (최종 결정권)
    │              vehicle_app.c · control.c : 허용 시 구동, HB 감시
    ├ 서보(문 잠금) · 문 스위치 · OLED · LED · 반납 버튼
    └ MDD3A → TT 모터 4개 (시동 표시)
```
- 실험에서는 **서버↔차량만 끊고**(`app.py net off` 또는 방화벽), 앱↔차량은 유지한다.
- 휴대폰 앱은 만들지 않는다. 노트북 스크립트가 앱 역할을 한다.
- Pi의 AI 판정은 STM32의 제한을 **풀 수 없다** (방식 F에서 보류 판단에만 사용).

## 4. 역할
- 아래는 **주로 맡는 영역**이다. 고정 분담이 아니며, 일정과 상황에 따라 필요한 사람이 맡는다 (10/28 Pi·보드 공동 작업처럼).
- 정해진 것은 세 가지다: **PM·문서 관리 = 권기백**, **부스 설명 담당 = 미정**(중간발표는 포스터 발표, §15. 11/3 곽동규 본인 정정: 발표자 아님), **STM32 빌드·업로드 = 김채희 노트북 1대** (§9).
- 누가 하든 00·공유 코드 변경은 요청으로 올리고, 한 일은 작업 MD(01 양식)로 남긴다 (§12).

| 이름 | 주로 맡는 영역 | 관련 파일 |

## 5. 메시지 형식 (확정)
- **텍스트 한 줄:** `RID|종류|필드...\n`
  - RID = 2자리 16진수 요청 ID이고, 응답은 같은 RID를 돌려준다.
- 숫자와 바이트는 **대문자 16진수, 고정 길이**로 쓴다.
- VID·KID 4바이트(8자), NONCE 16바이트(32자), TAG 32바이트(64자)
- `#`으로 시작하는 줄은 STM32 디버그 로그다(Pi가 화면에만 출력).
  - **문 상태 로그 (11/6):** 보드는 문 스위치 디바운스 값이 바뀔 때 `# DOOR STATE OPEN` / `# DOOR STATE CLOSED`를 낸다(부팅 뒤 첫 값부터). 프로토콜 메시지가 아니라 로그이며 판단에 쓰지 않는다. `pi_relay.py`가 이 로그와 `DOOR CLOSED -> LOCK ACT=` 로그를 읽어 **TCP `--port`+1(기본 9101)**에 `DOOR|state|seq|lock` 한 줄로 알려 주고, 웹 화면이 0.4초마다 읽어 3D 문으로 그린다(시연 표시용)
- 한 줄 최대 **512자** (SYNC 줄이 길다). 부품 시험용 명령은 시험 빌드에서만 허용한다.

| 방향 | 메시지 |
|---|---|
| 앱→차 | `KEY|KID|EXP|LIMIT|SIT|PERM|TAG` 키 등록 |
| 차→앱 | `KEYOK|KID` / `KEYNG|KID|사유` |
| 앱→차 | `REQ|KID|CMD` (CMD 01 문열기, 02 시동, 03 반납) |
| 차→앱 | `CHAL|KID|NONCE` (5초, 1회용) |
| 앱→차 | `RESP|KID|CMD|NONCE|TAG` |
| 차→앱 | `RES|KID|결과|사유|남은횟수` (결과 A 허용 / D 거부 / H 재검증 대기, 남은횟수 FF=제한 없음). 세 결과는 OLED·CSV에 구분 표시 |
| Pi→차 | `RID|HB` 생존 신호, 250ms마다, 응답 없음. 2초 끊기면 모터 정지 (제어 보호용, 정책상 오프라인과 별개) |
| 차→서버 | `SYNCREQ|VID|NONCE|VER` (STM32가 2초마다 스스로 송신) |
| 서버→차 | `SYNC|VID|VER|NONCE|COUNT|KID:ST,KID:ST,...|TAG` (ST 00 유효, 01 취소) |
| 차→서버 | `SYNCACK|VID|VER` |
| 앱→서버 | `ISSUE|KID|EXP|LIMIT|SIT|PERM`, `REVOKE|KID`, `NET|0/1` (시연용 차단) |

### 인증값 (HMAC-SHA256, 입력은 바이트, 정수는 빅엔디언)
- 개별 키: `k_i = HMAC(K_v, "user" ‖ KID)`
- 응답: `TAG = HMAC(k_i, VID ‖ KID ‖ CMD ‖ NONCE)` (25바이트)
- 키 등록: `HMAC(K_v, "KEY" ‖ VID ‖ KID ‖ EXP ‖ LIMIT ‖ SIT ‖ PERM)`
- 동기화: `HMAC(K_v, "SYNC" ‖ VID ‖ VER ‖ NONCE ‖ COUNT ‖ (KID ‖ ST)*)`
- K_v는 서버와 STM32만 가진다. 개발용 값은 `00 01 … 1F`이며 실제로 쓰면 안 된다.
- **정답표:** `hmac_vectors.txt`. STM32 결과가 이것과 같아야 한다.

### 사유 코드
| 코드 | 의미 | 코드 | 의미 |
|---|---|---|---|
| 00 | 정상 | 05 | 오프라인 횟수 초과 |
| 01 | 인증값 불일치 | 06 | 권한 없음 |
| 02 | nonce 만료·재사용 | 07 | 재검증 대기 |
| 03 | 취소된 키 | 08 | 등록되지 않은 키 |
| 04 | 유효기간 만료 | 09 | 반납된 키 |

## 6. 차량 판단 규칙 (core.py = sharekey.c, 반드시 동일)
1. 판단 순서: **등록 → 인증값 → nonce → 취소/반납 → 기간 → (반납 명령 처리) → 권한 → 횟수 → 실행**
2. nonce는 성공/실패와 관계없이 1회용이다.
3. 횟수는 **차감 → (저장) → 실행** 순서로 처리하고, 실행이 실패해도 차감한다.
4. 오프라인 횟수는 **마지막 인증된 동기화 이후** 사용 수다. 인증된 SYNC만 횟수를 복구하며, 단순 재접속으로는 복구하지 않는다.
5. 동기화는 NONCE가 자기가 보낸 값과 같고, VER ≥ 현재값이고, TAG가 맞을 때만 반영한다.
6. 취소된 키는 동기화로 되살아나지 않는다. 반납(03)은 차량 내부 상태라 서버보다 우선한다.
7. 같은 KID를 다시 등록하면 기존 기록(남은 횟수·상태)을 유지한다.
   - **7-1 (11/5 확인, 알려진 구멍):** 기록이 RAM에만 있어 **재부팅 뒤에는 7번이 소용없다.** 이용자는 서버가 서명한 KEY 줄을 갖고 있으므로, 취소된 키로 오프라인 4회를 다 쓴 뒤 차 전원을 껐다 켜고 재등록하면 횟수가 다시 limit이 된다. 즉 지금의 C는 재부팅당 상한이지 총 상한이 아니다. 내부 플래시 저장(§8, 11/16) 뒤 **"재부팅·재등록 후 남은 횟수가 늘지 않음"**을 T04 시험 항목으로 둔다. 그전까지 발표·문서에 한계로 명시한다.
8. 만료는 발급 때 정하고 동기화로 연장하지 않는다.
10. **오프라인 판정 (면담 숙제 2):** 지금 구현은 차가 **2초마다 SYNCREQ(새 nonce)**를 보내고 서버가 그 nonce를 넣어 서명한 SYNC로 답하는 **하트비트 + 인증된 ACK** 구조다. 다음 주기까지 응답이 없으면 `no server response -> OFFLINE`, 인증된 SYNC가 오면 `ONLINE`. 즉 교수님이 말한 왕복(request/ack) 방식이 이미 있고, 가짜 ACK는 서명·nonce로 걸러진다. **보완할 것:** ① 1회 미응답으로 바로 OFFLINE은 민감 → 연속 K회(초안 3회 = 6초) 미응답으로 판정, ② 차가 배터리 때문에 **스스로 통신을 끄는 경우**(블루링크 48~336h)는 자기 이벤트이므로 그 시각부터 오프라인으로 계산, ③ Pi→STM32 HB(250ms)는 제어 안전용이며 정책상 오프라인과 별개(§5). 쏘카의 실제 판정 방식은 조사 중(공개 자료 없음)
11. 보류(H)·이상 판정은 방식 F와 E+단순 규칙에서만 쓰며(11/16 이후), 같은 키로 재인증하는 것만으로는 보류가 풀리지 않는다. AI 정상 판정은 제한을 풀 수 없다.

### 6.1 제어 계층 규칙 (control.c, 판단 규칙과 별개)
- 부팅 시 자동 구동하지 않는다.
- 모터는 문 닫힘·잠금 확인 후 돈다. 서보는 바퀴가 멈춘 상태에서 움직인다.
- 모터 구동 중 문·잠금 입력이 사라지거나, 생존 신호가 2초 끊기거나, 서보가 시간 안에 끝점에 못 가면 정지하고 오류를 유지한다.
- **다시 잠그기 (11/1 결정):** 문열기(01) 허용으로 잠금이 풀린 뒤, 문 닫힘 스위치(PF12)가 **열림 → 닫힘**으로 바뀌면 서보를 잠금 위치로 돌린다. 메시지 형식·판단 규칙은 바꾸지 않는다(제어 계층 동작). **11/5 판정: 사용.** 김채희 11/4 실물(§9): 온라인 5회 연속 해제↔잠금, Pi 경유 오프라인 C를 다시 잠그기까지 오류 없이 1회. 문짝 부착 뒤 10회 반복은 남음. (이전: 11/2 곽동규 구현·PC 시험, "중간발표 전 구현" 결정)
  - 구현: v2 `vehicle_app.c`에서 디바운스된 문 닫힘 에지 → `ACT_LOCK`. 설정 `VC_RELOCK_ON_DOOR_CLOSE`(기본 1, 0이면 이전 동작). 기존 안전 조건(문 닫힘 상태에서만 잠금, HB 유지, 오류 시 구동 안 함) 유지
  - 조건: 활성(armed)·오류 없음·**UNLOCKED 상태**일 때만. 부팅 후 첫 디바운스 값은 기준값이라 동작하지 않는다. 막힌 닫힘 에지는 버리고 나중에 다시 시도하지 않는다
  - **위치 UNKNOWN(부팅 직후)에서는 잠그지 않는다** (11/3 확정). 부팅 후 첫 허용으로 해제된 뒤부터 동작한다
  - 잠그는 중 문이 열리면 기존대로 FAULT_DOOR(오류 유지). 잠금은 키 횟수를 차감·복구하지 않는다
  - **조작 규칙 (11/4 곽동규·김채희):** 다시 잠그기는 스위치의 **열림→닫힘 변화**로만 일어난다. 처음부터 계속 눌러 두면 잠그지 않는다. 매회 "해제 끝 → 스위치 뗌 → 다시 누름 → 잠금 끝(0.5초 이상)까지 눌린 채 유지". 잠그는 중 떨어지면 FAULT_DOOR → RESET·재등록. 문짝은 **열면 스위치가 떨어지고 닫으면 계속 눌리는 구조**로 만든다(자석 또는 케이스 걸쇠)
  - (이전 조건 "11/5까지 안 되면 첫 해제만"은 판정으로 해소)
- 임시값(실물에서 보정): 서보 50Hz·1200/1800μs, 모터 PWM 10kHz·상한 60%, 디바운스 30ms, 서보 제한 1.5초

- 탐색 후보: 횟수 2·4·8·16, 기간 2·6·24·72h
- 정상 사용자 거부율 5% 이하를 초기 기준으로 한다.
- **현실 조건 (면담 숙제 3) — 최종 알고리즘 과제:** 쏘카처럼 시간을 미리 결제하면 **대여 기간(EXP) 안의 오프라인은 정상**이다(S9). 횟수 제한은 결제 기간 안의 정상 이용자를 막으면 안 되고, **취소·조기 반납 이후**의 사용과 **기간 종료 이후**의 사용을 막아야 한다. 초안 "D-현실": (가) EXP 안 + 오프라인 → 허용하되 **시동 뒤 운행 시간/거리 상한**(S3) (나) EXP 종료 → 유예 M분 뒤 거부 (다) 조기 반납(03)은 차 내부 즉시 무효 (라) 오프라인 횟수 N은 EXP 밖 또는 반납 뒤의 "잔여 사용"에만 적용. 값·조건은 쏘카 요금제 조사 뒤 정한다
- **비교 표 (최종 목표, §1 네 축으로 채운다. 11/5):**

| | A 서버 취소만 | B 기간 | C 횟수 | D 기간+횟수 |
|---|---|---|---|---|
| ① 폐기 후 최대 사용 | 무제한 | 남은 기간 | 남은 횟수 (실물 4회, 1회 시행) | 둘 중 먼저 끝나는 것 |
| ② 정상 이용자 오프라인 허용 | 무제한 | 기간 안 무제한 | 횟수까지 | 둘 다 안에서 |
| ③ 갱신 통신량 | 공통(SYNC) | 공통 | 공통 | 공통 |
| ④ 재부팅·시계 | — | 시계 되돌림 | **재부팅 재등록(§6 7-1)** | 둘 다 |
  - 설계상 예상값이며 측정값이 아니다. 측정값이 들어오면 칸마다 "(측정, n회)"로 바꾼다
  - **③ 갱신 통신량 계산값 (11/6 정정):** 2초마다 SYNCREQ 62B + SYNC 약 128B + 키당 12B + SYNCACK 29B = **약 220B + 키당 12B**. 키 8개면 1분에 약 **9.4KB**(30회 × 316B). 메시지 형식(§5)으로 센 계산값이며 실물 Pi 로그로 잰 값이 아니다(T08). 이전 문서·면담자료의 "180B + 키당 11B, 약 8KB/분"은 SYNCACK을 빼고 센 값이라 이 값으로 바꾼다

## 12. 개발 규칙
0. 결정이 필요한 새 문제가 생기면 코드를 바꾸기 전에 팀장에게 알리고, 결정 후 이 문서에 반영한다.
1. AI에게 작업을 시킬 때 **이 문서를 먼저 붙여 넣고** "이 문서의 메시지 형식, 판단 규칙, 핀 배치를 벗어나지 말 것"이라고 지시한다.
2. 작업이 끝나면 **코드와 함께 작업 MD**(`01_양식_개인작업.md` 형식)를 팀장에게 준다. 코드만 주지 않는다.
3. 메시지 형식, 판단 순서, 사유 코드를 바꾸면 Python(core.py)과 C(sharekey.c)를 **둘 다** 고치고, `demo.py --relay-c` 결과가 같은지 확인한다.
4. 디버깅은 로그로 한다. 시리얼 로그를 복사해 AI에게 주고, 필요한 로그를 추가해 다시 돌린다.
5. 하드웨어 핀은 사진을 찍어 AI에게 확인받되, 결과는 §8 핀표에 반영한다.
6. 코드와 MD는 GitHub 저장소 하나에서 관리한다.

### 15.2 시연 (부스 책상)
- 구성: 노트북 **웹 화면(`web_app.py`, 11/4 차량 앱 형태로 개편)** + 차 모양 모듈(4WD **아래판**에 보드·건전지(밑면)·OLED, 문짝 = **다이소 투명 경첩 케이스 뚜껑**(11/5, 우드락 대신) + 서보 걸쇠 + 택트 스위치(닫히면 계속 눌림, 걸쇠·자석), Pi는 차 옆) + Pi 5. 화면은 노트북을 그대로 보여 준다
- **A·C 모두 현장 실물:** 보드 1개에서 **USER 버튼으로 방식 전환** — 그냥 RESET = C, USER 누른 채 RESET 후 손 떼기 = A (후보판 `stm32_vehicle_control_f429_v2_1103`, 발표용 빌드에서 `VC_DEMO_MODE_SELECT 1`). RESET하면 키가 지워지므로 전환 후 등록부터
- **A 영상은 예비용**(버튼 전환이나 보드에 문제가 있을 때)
- **반복 시연:** 방문자마다 서버를 다시 켜지 말고 **공유 키 번호만 바꿔** 발급·등록(7, 8, 9…). 한 번에 1~2분: 등록 → 문 열기(+문 닫기) → 2초 이상 뒤 **차량 오프라인** → 몇 초 뒤 취소 → 문 열기 6번 → **차량 온라인** → 몇 초 뒤 문 열기(03)
- 다시 잠그기(§6.1, 11/5 사용 확정): 허용되면 걸쇠가 풀리고 사람이 문을 열었다 닫으면 잠긴다. 거부되면 걸쇠가 그대로라 당겨도 안 열린다. **문은 매번 실제로 열었다 닫아야** 다시 잠근다(스위치 변화). OLED가 멈추면 5~10초 대기 → 보드 RESET → OLED 전원 재투입 순서로 풀고 몇 번째에서 풀렸는지 기록
- **IP 규칙 (11/6 김채희 정리):** Pi에서 `pi_relay.py --server <노트북 IP>`, 노트북에서 `web_app.py --vehicle <Pi IP>`. 문 3D 표시는 Pi의 9101 포트(§5)를 읽으므로 같은 Pi IP를 쓴다(`--door`로 따로 줄 수 있음). 장소가 바뀌면 두 IP를 다시 확인
- 처음 켜는 순서: 서버(상태 초기화) → Pi 중계 → 보드 RESET → 웹 화면. 서버·중계를 다시 켜면 보드 RESET. 전원: 켤 때 USB → 건전지, 끌 때 건전지 → USB
- **현장 콘센트 확인**(Pi USB-C 전원, 노트북). 없으면 보조배터리

### 15.3 표현·표기
- 제목: 취소해도 남는 공유 차 키 — 오프라인 차량을 위한 차량 측 사용 제한 모듈 설계
- 기능 블록도에서 노트북–Pi 연결은 빨간 점선 "실험 시 차단", STM32는 "최종 판단"으로 강조. 제안 발표의 블록도·흐름도·일정 그림 재사용
- 예시 데이터는 정답표 값 사용 (공유 키 번호 7 등). 청중용 화면·포스터에서는 KID 대신 "공유 키 번호", 서버 끊기·연결은 **"차량 오프라인/차량 온라인"**(예: 지하주차장, 오래 시동을 걸지 않아 통신이 멈춘 경우 — §1 블루링크 48~336h). 시연 버튼은 서버의 동기화 응답 중단(`app.py net off`)이며 실제 장시간 주차를 재현한 것이 아니다
- 측정하지 않은 목표를 결과처럼 쓰지 않는다. 실물 결과는 각 1회 시행으로 표시하고, 서보·저장 등 확인 안 한 기능은 완료로 쓰지 않는다. 보드는 NUCLEO-F429ZI로 표기
- 쓰지 않는 말: "오프라인 취소 탐지", "성능 목표 달성", "재부팅해도 유지", "시동 구현"(판단만, 모터 꺼짐), C를 우리 아이디어로 소개(기존 방식, 비교 대상), **"피해 상한 보장"**(재부팅 재등록 구멍이 남아 있음 — "재부팅당 상한"으로)
- 한계는 먼저 말한다: 마스터키 개발용 고정값, 메시지 암호화 없음, 키 RAM 저장(재부팅 재등록), 근접성 검증 범위 밖
- 발음: UART=유아트, STM32=에스티엠 삼십이, HMAC=에이치맥, nonce=논스
