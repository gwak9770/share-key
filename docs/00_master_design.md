## 1. 주제와 문제
- **주제:** 취소해도 남는 공유 차 키 — 오프라인 차량을 위한 차량 측 사용 제한 모듈
- **한 줄 요약:** 카셰어링·렌터카 이용이 끝난 뒤 남는 디지털 차 키를, 서버와 연결이 끊긴 차량이 스스로 제한·만료시키는 모듈
- **핵심 기여 (11/4 결정):** 서버와 통신이 끊긴 차량이 스스로 공유 키 사용을 제한하는 모듈을 실제 보드로 구현하고, 여러 제한 방식을 같은 조건에서 비교해, 차를 공유할 때 어떤 제한 방식을 고르는 것이 좋은지 판단할 근거를 제공한다.
  - 포스터용 짧은 판: "끊긴 차도 스스로 지키는 공유 키 — 제한 방식을 같은 조건에서 비교해 '어떻게 공유할지' 선택을 돕는다."
  - 방식 C(오프라인 횟수)·B(기간)는 기존 방식이며 비교 대상이다. 중간발표는 A·C 실물 비교, 최종은 A~D(+E) 비교(T06)로 상황별 추천. 비교 결과가 나오기 전에는 "판단할 근거를 제공한다/도울 수 있다"로 쓰고 "도움을 줬다"로 쓰지 않는다
- **연구 초점과 평가 축 (11/5 결정, 지도교수 자료 §2.4 "키 공유·폐기"를 따른다):** 차량이 오프라인이면 방금 서버에서 한 폐기를 즉시 알 수 없다는 구조적 한계를 인정하고, "즉시 폐기"가 아니라 아래 네 가지를 **방식별로 정량화**해 비교한다. 지금까지의 "6회 중 몇 회 허용"은 ①의 한 칸이다.
  | 축 | 뜻 | 지금 상태 |
  |---|---|---|
  | ① 폐기 후 최대 사용 | 취소된 키로 오프라인에서 더 쓸 수 있는 **횟수·시간** | 횟수(C 4회)만 실물 1회. 시간 축은 RTC 뒤(B·D) |
  | ② 정상 이용자 오프라인 허용 | 취소 안 된 이용자가 오프라인에서 쓸 수 있는 횟수·시간 (= 제한의 비용) | 미측정. C는 정상 이용자도 4회 뒤 05 |
  | ③ 갱신 통신량·전력 | SYNC 주기·크기, 전력 | 미측정(계산값부터) |
  | ④ 재부팅·시계 견고성 | 재부팅·재등록·시계 되돌림으로 상한이 무너지지 않는가 | **재부팅 시 초기화됨(§6 7-1, 알려진 구멍)**, 시계는 RTC 뒤 |
  - 같은 자료의 근접성 검증(§2.1~2.3 릴레이·UWB·전환), 계정·클라우드(§2.5), VSOC 탐지(§2.6)는 **범위 밖**이다. 휴대폰↔차 근거리 구간은 정당한 근접으로 가정한다
  - 방식 F(AI 보류)·E+는 §2.6 탐지 쪽에 가까워 **최종 범위에서 "확장 가능성"으로 내린다**(§7). 시간이 남으면 되살린다
- **11/5 지도교수 면담 결과 (녹취 기준):** 주제는 좋고 더 키울 수 있다("졸업작품으로만 묻기 아깝다", 쏘카 등 카셰어링 업체 세일즈·특허·기술 이전까지 가능). **지금 시험은 그대로 진행**하되, 아래 세 숙제의 답을 누군가 준비할 것. 시연은 Pi 연결 문제로 못 보여 드림 → 다음 면담 때
  1. **오프라인에서 생길 수 있는 문제를 구체화** — "더 오래 쓴다"에서 끝내지 말고 도난·해외 반출·금전 이득 등 **더 심각한 결과**로 이어지는지. 특히 A(보안 없음)를 더 분석해 필요성으로 연결 (§1.2)
  2. **차가 스스로 오프라인임을 어떻게 아는가** — B·C 모두 시작점이 "오프라인 판정"인데 답이 없었음. 하트비트 + ACK(왕복)로 끊김을 인식하는 방식, 쏘카가 실제로 어떻게 하는지 조사. 우선은 "감지했다고 가정"하고 병렬 진행 가능 (§6 10)
  3. **현실 조건 반영** — 쏘카처럼 시간을 미리 결제하는 경우 **결제한 기간 안의 오프라인은 문제가 아닐 수 있다.** 지금 C는 돈을 낸 정상 이용자도 잠근다. 대여 기간을 고려한 최종 알고리즘 하나는 있어야 함 (§7 현실 조건)
  4. 결과 제시는 **방식 1(공격 시나리오별 방어 여부)을 더 깊게** — 잘 알려진 공격이 아니라 **공유차 특성(이용자가 계속 바뀜, 이용자 사이 공백, 그사이 오프라인)**을 파고드는 공격을 찾아 방식별로 평가 (§2.1). 방식 2(시간 대비 피해량)는 보조
- **11/9 중간발표 결과:** 지적사항 없음. 지금 방향(키 공유·폐기 집중, 방식 비교, 공유차 시나리오)을 유지하고 최종발표까지 02 로드맵대로 진행한다.

### 1.1 최종 결론 — 공격 중심 (11/28, 면담 방향 "도난까지 가는 공격을 막는가, 쏘카에 팔 수 있는가")
숫자는 모두 **PC 모의**(`docs/results/summary.md`·`recommend.md`, 조건 28개)이고, 따로 적은 것만 PC 시험·실물이다. 보드에서 B(기간)는 RTC 통합 뒤 확인한다(02 §10).

1. **틈은 실제로 있다.** 쏘카 차량은 서버가 끊겨도 블루투스로 열리고, 2023 KT 장애 때 쏘카가 그 방법을 직접 안내했다(§1.2). 오프라인은 공격자가 만들 수 있다(지하, 안테나 분리, 전파 차단).
2. **지금 방식(A, 서버 취소만)은 뚫린다.** 취소된 키로 오프라인 중 시도한 157번 중 **막은 것 0번(0%)**. 취소가 닿지 않는 동안 문·시동이 모두 열려 L1 무단 사용부터 L5 도난·반출까지 이어진다(§1.2 표).
3. **우리 모듈 (추천 구성):** B 대여 기간 확인 + 차량 반납 즉시 무효(§6 6) + 운행 중 재인증·정차 컷오프(§6 12) + 플래시 저장(§6.2).
   - **결제한 기간이 끝난 뒤 오프라인 시도 69번 중 69번 거부** (A는 69번 모두 허용).
   - **정상 이용자 불편 0%:** 결제 기간 안의 오프라인 시도 127번 중 거부 0번. 횟수 방식 C(N=4)는 같은 조건에서 48%를 막았다.
   - **도난 운행:** 재인증이 실패하면 경고하고, 정차가 10분 이어지면 시동을 해제한다. 정차 컷오프 뒤 재시동 허용 0 (PC 모의), 재시동 07 거부 실물 1회(11/19). 재인증을 켠 조건에서 관찰 구간 대비 시동 켜진 시간은 A 66%, B 23%(S3).
   - **재부팅 공격:** 상태를 플래시에 저장해 재부팅·재등록 뒤 횟수 N 초과 15/28 → 0/28 (C N=4, PC 모의), 남은 횟수 증가 0 (PC 시험 30회). 보드 재부팅 복원 실물은 남음.
4. **한 줄:** "우리 모듈이 없으면 취소된 키로 차를 끌고 가도 차는 모른다. 우리 모듈이 있으면 기간이 끝난 키는 문과 시동이 거부되고, 끌고 가던 차는 정차 10분 뒤 다시 출발하지 못하는 것이 목표다." (PC 모의로 확인, 보드는 RTC 통합 뒤)
5. **남은 틈 (숨기지 않는다):**
   - **기간 안 취소:** 결제 기간 중 서버에서만 취소된 키는 B가 막지 못한다(오프라인 시도 88번 허용). 차에서 반납하면 즉시 09로 막힌다. 기간 안까지 막으려면 D(N=4)·D-현실(24시간)처럼 막는 비율이 70%·62%로 오르지만 정상 이용자 거부율도 48%·7.1%로 오른다. 이 선택은 운영사 몫이며 비교 결과로 근거를 준다.
   - **달리는 중에는 끄지 않는다.** 안전을 위한 설계다. 정차 전까지 운행 시간 상한은 없다.
   - **시계 되돌림(S7):** B는 차량 시계를 믿는다. 11/28 시계 하한 규칙(§6 13)으로 전원이 켜진 동안·마지막 저장 시각 이전으로의 되돌림은 04로 거부한다(PC 시험). 전원을 꺼 둔 시간만큼은 기간이 늘어날 수 있다.
   - **키 복사(L6):** 키별 상한만 있다.
6. **쏘카가 쓸 이유:** 정상 고객 불편 0%(위 3), 통신량은 키 1개일 때 2초에 232바이트(계산값, §7), 새 서버 없이 차량 단말의 판단 규칙으로 들어간다. Python과 C 판단이 대표 30개에서 30/30 같다(PC, `docs/results/c_equiv.md`).

### 1.2 오프라인에서 생길 수 있는 문제 — 나쁜 마음을 먹으면 어디까지 가나 (면담 숙제 1, 11/5 저녁 보강)
**핵심 통찰: 오프라인은 "우연히 생기는 상태"가 아니라 공격자가 만들 수 있는 상태다.** 지하주차장으로 옮기기, 통신 모듈 퓨즈·안테나 분리, 전파 차단 가방·재머, 서버 장애 시간대 노리기, 차가 스스로 통신을 끄는 장시간 주차(블루링크 48~336h) 기다리기. 공격자가 오프라인 시점을 고를 수 있으므로 "오프라인은 드물다"는 가정은 쓰지 않는다.

**공격자 (누가):** ① 정당하게 빌렸다가 취소된 전 이용자 ② 남의 명의로 빌린 사람(실제 사례, 2017 광주 무면허 17세·명의 도용 반복) ③ 전 이용자가 키를 넘긴 공범 ④ 발레·대리 같은 잠깐 맡은 사람

| 단계 | 공격 사슬 | 피해 | A 서버 취소만 | 우리 모듈 (B + 반납 무효 + 재인증 + 플래시, 11/28) |
|---|---|---|---|---|
| L1 무단 사용 | 취소된 키로 문 열고 시동 | 요금 미납·사고 책임 혼선 | **열림.** 오프라인 중 시도 0/157 거부 (PC 모의) | 기간 끝 뒤 69/69 거부 (PC 모의). 기간 안 서버 취소는 허용(88번) — 남은 틈 |

| L5 도난·반출 | L4 상태로 컨테이너·항구 이동, **해외 반출·부품 판매**. 테슬라 렌터카 사례: 반납 후 인증이 제거됐는데도 앱으로 잠금 해제·시동, GPS 끄려 시도, 충전 기록으로 추적·체포 | 차량 가치 전체 | **뚫림** | 옮기려면 정차가 생기므로 L4처럼 그 자리에서 재출발 거부. 배터리 분리·재부팅 뒤에도 07·취소·횟수를 플래시에서 복원 (PC 모의·PC 시험, 보드 실물 남음). 시계 되돌림(S7)은 시계 하한으로 04 거부(§6 13, PC 시험), 전원을 꺼 둔 시간만큼은 한계 |

  - 차량 단말 STS가 **서버 명령과 블루투스 명령을 모두 받고, 블루투스가 되면 블루투스를 먼저 쓴다.** 명령은 "정합성 및 보안성을 검사한 뒤" 실행하고, 단말은 연결 유지용 주기 신호(aliveMessage)를 보낸다([쏘카 기술 블로그 2026-01-08](https://tech.socar.kr/socarframe/2026/01/08/socarframe-bluetooth)).

  - 예약은 최소 30분부터 10분 단위, 1회 최대 28일, 연장은 앱으로 한다(앱스토어 소개).
  - **공개 자료에 없는 것:** 블루투스 명령 검증 방법(키·만료·재전송 방지), 차량이 예약 기간을 직접 확인하는지, 취소·반납이 차량에 반영되는 방법, 오프라인 판정 기준, 오프라인 사용 제한.
- 업계 방식 (공개 자료, 대부분 업체 소개 글이라 기술 명세가 아님): INVERS는 예약 시작 때 기간이 정해진 블루투스 토큰을 휴대폰에 주고 차량 단말이 확인하며, 유효기간은 운영사가 정하고 늦게 반납하는 이용자를 잠그지 않는다([INVERS](https://invers.com/en/blog/4-car-sharing-telematics-myths/)). MoboKey는 대여 기간이 끝나는 순간 키가 만료된다([MoboKey](https://mobokey.com/how-digital-keys-enable-contactless-car-rentals-with-mobokey/)). CCC 디지털 키는 공유 키에 시작·만료 시각을 두고 오프라인 동작을 위해 권한을 저장하지만, 취소에는 연결이 필요할 수 있고 차량에서 키를 지우는 방식은 제조사마다 다르다([CCC](https://carconnectivity.org/?p=17)). → 기간을 정한 키를 차가 확인하는 B 방향, 운행 중 끄지 않는 D1과 같은 흐름이다. 취소된 키의 오프라인 사용량을 방식별로 비교한 공개 자료는 찾지 못했다
- 포스터 ② "문제" 장: L1→L5 사슬 그림 + 테슬라 사례 한 줄

## 3. 전체 구조
```
[노트북] server.py (발급·취소·버전) + app.py (주인/받는 사람 앱 대신)
    │ TCP 9000 (동기화)          │ TCP 9100 (앱 요청)
    ▼                            ▼
[Raspberry Pi] pi_relay.py : 줄을 그대로 전달만 함 (판단 없음)
    │ USB (ST-LINK 가상 COM, 115200 8N1)
    ▼
[NUCLEO-F429ZI] sharekey.c : 인증·판단 (최종 결정권)
    │              vehicle_app.c · control.c : 허용 시 구동, HB 감시
    ├ 서보(문 잠금) · 문 스위치 · OLED · LED · 반납 버튼
    └ MDD3A → TT 모터 4개 (시동 표시)
```
- 실험에서는 **서버↔차량만 끊고**(`app.py net off` 또는 방화벽), 앱↔차량은 유지한다.
- 휴대폰 앱은 만들지 않는다. 노트북 스크립트가 앱 역할을 한다.
- Pi의 AI 판정은 STM32의 제한을 **풀 수 없다** (방식 F에서 보류 판단에만 사용).

- 숫자와 바이트는 **대문자 16진수, 고정 길이**로 쓴다.
- VID·KID 4바이트(8자), NONCE 16바이트(32자), TAG 32바이트(64자)
- `#`으로 시작하는 줄은 STM32 디버그 로그다(Pi가 화면에만 출력).
  - **문 상태 로그 (11/6):** 보드는 문 스위치 디바운스 값이 바뀔 때 `# DOOR STATE OPEN` / `# DOOR STATE CLOSED`를 낸다(부팅 뒤 첫 값부터). 프로토콜 메시지가 아니라 로그이며 판단에 쓰지 않는다. `pi_relay.py`가 이 로그와 `DOOR CLOSED -> LOCK ACT=` 로그를 읽어 **TCP `--port`+1(기본 9101)**에 `DOOR|state|seq|lock` 한 줄로 알려 주고, 웹 화면이 0.4초마다 읽어 3D 문으로 그린다(시연 표시용)
- 한 줄 최대 **512자** (SYNC 줄이 길다). 부품 시험용 명령은 시험 빌드에서만 허용한다.

| 방향 | 메시지 |
|---|---|
| 앱→차 | `KEY|KID|EXP|LIMIT|SIT|PERM|TAG` 키 등록 |
| 차→앱 | `KEYOK|KID` / `KEYNG|KID|사유` |
| 앱→차 | `REQ|KID|CMD` (CMD 01 문열기, 02 시동, 03 반납, **04 운행 중 재인증, 05 시동 끄기** — 04·05는 11/18 추가, D1) |
| 차→앱 | `CHAL|KID|NONCE` (5초, 1회용) |
| 앱→차 | `RESP|KID|CMD|NONCE|TAG` |
| 차→앱 | `RES|KID|결과|사유|남은횟수` (결과 A 허용 / D 거부 / H 재검증 대기, 남은횟수 FF=제한 없음). 세 결과는 OLED·CSV에 구분 표시 |
| Pi→차 | `RID|HB` 생존 신호, 250ms마다, 응답 없음. 2초 끊기면 모터 정지 (제어 보호용, 정책상 오프라인과 별개) |
| 차→서버 | `SYNCREQ|VID|NONCE|VER` (STM32가 2초마다 스스로 송신) |
| 서버→차 | `SYNC|VID|VER|NONCE|COUNT|KID:ST,KID:ST,...|TAG` (ST 00 유효, 01 취소) |
| 차→서버 | `SYNCACK|VID|VER` |
| 앱→서버 | `ISSUE|KID|EXP|LIMIT|SIT|PERM`, `REVOKE|KID`, `NET|0/1` (시연용 차단) |

- **CMD 04·05 (11/18, D1):** 흐름은 다른 명령과 같다(`REQ` → `CHAL` → `RESP` → `RES`). 권한은 **시동 권한(PERM 0x02)**을 따르므로 KEY 형식·PERM 비트는 바꾸지 않는다. 거부 사유는 기존 코드를 쓴다(재검증 대기 07). C/Python PC 구현·시험, 보드 빌드·실물 미수행(§6 12).

### 인증값 (HMAC-SHA256, 입력은 바이트, 정수는 빅엔디언)
- 개별 키: `k_i = HMAC(K_v, "user" ‖ KID)`
- 응답: `TAG = HMAC(k_i, VID ‖ KID ‖ CMD ‖ NONCE)` (25바이트)
- 키 등록: `HMAC(K_v, "KEY" ‖ VID ‖ KID ‖ EXP ‖ LIMIT ‖ SIT ‖ PERM)`
- 동기화: `HMAC(K_v, "SYNC" ‖ VID ‖ VER ‖ NONCE ‖ COUNT ‖ (KID ‖ ST)*)`
- K_v는 서버와 STM32만 가진다. 개발용 값은 `00 01 … 1F`이며 실제로 쓰면 안 된다.
- **정답표:** `hmac_vectors.txt`. STM32 결과가 이것과 같아야 한다.

### 사유 코드
| 코드 | 의미 | 코드 | 의미 |
|---|---|---|---|
| 00 | 정상 | 05 | 오프라인 횟수 초과 |
| 01 | 인증값 불일치 | 06 | 권한 없음 |
| 02 | nonce 만료·재사용 | 07 | 재검증 대기 |
| 03 | 취소된 키 | 08 | 등록되지 않은 키 |
| 04 | 유효기간 만료 | 09 | 반납된 키 |

### 5.1 저장 장애 복구 메시지 (2026-11-18 구현 후보)
- RID 포함 규칙은 그대로다. 사유 `0A` = 저장 장애·복구 필요(기존 07과 구분). CMD 04·05는 §6 12의 운행 소유 세션 규칙을 따른다.
- 앱→차 `RBEGIN`, 차→앱 `RCHAL|VID|NONCE`. 저장 사용 중 복구 필요 상태에서만 허용. 난수 128비트, 현재 부팅 중 1개 유지(일반 인증 5초 제한 미적용). 반복 요청은 같은 값, 재부팅·복구 성공 시 무효.
- 앱→서버 `RISSUE|VID|NONCE|OLDKID|NEWKID|PROOF`. PROOF = HMAC(k_i(OLDKID), `"RISSUE" ‖ VID ‖ NONCE ‖ OLDKID ‖ NEWKID`). 서버는 차량 번호·키 소유 증명·기존 키 유효/미만료·미사용 새 번호 확인. 기존 키를 취소하고 기존 만료·횟수·상황·권한을 새 키에 부여한다. 동일 요청은 재발급하지 않고 기존 응답 반환(새 키가 제한됐으면 거부).
- 서버→앱 `RISSUED|VID|NONCE|VER|NEWKID|EXP|LIMIT|SIT|PERM|TAG|KI|KEYTAG`. TAG = HMAC(K_v, `"RECOVER" ‖ VID ‖ NONCE ‖ VER ‖ NEWKID ‖ EXP ‖ LIMIT ‖ SIT ‖ PERM`). KI는 이용자에게만 전달, KEYTAG는 일반 키 등록용 인증값.
- 앱→차 `RECOVER|VID|NONCE|VER|NEWKID|EXP|LIMIT|SIT|PERM|TAG`. 차→앱 `RECOVERED|NEWKID` 또는 `RFAIL|사유`. 서버 인증·현재 난수를 검증하고 새 키 1개와 VER 저장 후 성공 응답한다. 복구는 구동하지 않는다.
- 앱→서버 `RETURN|KID|PROOF`: PROOF = HMAC(k_i, `"RETURN" ‖ VID ‖ KID`). 서버는 반납 상태를 보관해 복구 발급을 거부한다. 동기화에서는 취소와 같이 ST=01로 전달한다. 차량만 반납하고 서버에 알리지 못한 경우 서버는 반납을 모를 수 있다.
- 앱 스크립트의 요청→발급→적용 명령으로 오프라인 운반을 시연한다. 네이티브 휴대폰 앱·상업용 본인/결제 확인은 미구현. 기존 발급/취소 API는 인증 없는 개발용이므로 실제 서비스 인증을 주장하지 않는다.

## 6. 차량 판단 규칙 (core.py = sharekey.c, 반드시 동일)
1. 판단 순서: **등록 → 인증값 → nonce → 취소/반납 → 기간 → (반납 명령 처리) → 권한 → 횟수 → 실행**
2. nonce는 성공/실패와 관계없이 1회용이다.
3. 횟수는 **차감 → (저장) → 실행** 순서로 처리하고, 실행이 실패해도 차감한다.
4. 오프라인 횟수는 **마지막 인증된 동기화 이후** 사용 수다. 인증된 SYNC만 횟수를 복구하며, 단순 재접속으로는 복구하지 않는다.
5. 동기화는 NONCE가 자기가 보낸 값과 같고, VER ≥ 현재값이고, TAG가 맞을 때만 반영한다.
6. 취소된 키는 동기화로 되살아나지 않는다. 반납(03)은 차량 내부 상태라 서버보다 우선한다.
7. 같은 KID를 다시 등록하면 기존 기록(남은 횟수·상태)을 유지한다.
   - **7-1 (11/5 확인, 알려진 구멍):** 기록이 RAM에만 있어 **재부팅 뒤에는 7번이 소용없다.** 이용자는 서버가 서명한 KEY 줄을 갖고 있으므로, 취소된 키로 오프라인 4회를 다 쓴 뒤 차 전원을 껐다 켜고 재등록하면 횟수가 다시 limit이 된다. 즉 지금의 C는 재부팅당 상한이지 총 상한이 아니다. 내부 플래시 저장(§8, 11/16) 뒤 **"재부팅·재등록 후 남은 횟수가 늘지 않음"**을 T04 시험 항목으로 둔다. 그전까지 발표·문서에 한계로 명시한다.
8. 만료는 발급 때 정하고 동기화로 연장하지 않는다.
10. **오프라인 판정 (면담 숙제 2, D4):** 기본 2초마다 새 난수로 SYNCREQ를 보낸다. 요청 뒤 다음 주기까지 인증된 SYNC가 성공하지 않으면 연속 실패를 1회 센다. **연속 3회(기본 주기 기준 약 6초)**일 때 OFFLINE으로 전환한다. 부팅 직후는 미확인(-1)이며 첫 요청 자체를 실패로 세지 않는다. 1·2회 실패 중에는 기존 온라인/미확인 상태를 유지한다. 반복 실패는 3에서 포화시키고 전환 로그는 한 번만 낸다.
   - 인증된 SYNC의 상태 저장까지 성공하면 실패 횟수를 0으로 만들고 즉시 ONLINE으로 복귀한다. 인증값·난수·버전·VID·형식이 틀린 응답, 다른 RID, Pi HB는 성공으로 세지 않는다. 잘못된 응답으로 nonce가 소모돼도 해당 주기의 미성공 대기는 남긴다.
   - 횟수는 기존 4번처럼 마지막 인증 동기화 기준이다. 3회 판정 전에도 사용은 차감하며 재접속·표시 전환만으로 복구하지 않는다. Pi HB 250ms/제어 보호 2초는 별개이며 변경하지 않는다.
   - 쏘카 공개 자료에는 단말의 주기 신호(aliveMessage)만 있고 오프라인 판정 기준은 없다(§1.2, 11/27 조사). 우리 3회 규칙은 면담 숙제 2의 "하트비트 + 응답 확인" 방식을 따른 자체 설계다.
   - C/Python 판단 코드와 직접/중계 모의 차량은 같은 3회 규칙을 따른다. 시험용 주기가 1초면 약 3초이며, 스케줄 지연 시 실시간 6초를 보장하지 않는다. 요청을 건너뛴 시간을 가상의 여러 실패로 세지 않는다. 실패 수·연결 상태는 저장하지 않고 재부팅·저장 복구 성공 시 초기화한다.
   - 저장 장애 복구 필요 중에는 동기화를 보내지 않으므로 실패를 누적하지 않는다. 스스로 통신을 끄는 차량 이벤트와 오프라인 지속 시간 제한(C-T)은 이번 구현 범위 밖이다. 실제 보드 시간·통신 시험은 미수행, PC 결과는 PR 본문에 기록한다.
11. 보류(H)·이상 판정은 방식 F와 E+단순 규칙에서만 쓰며(11/16 이후), 같은 키로 재인증하는 것만으로는 보류가 풀리지 않는다. AI 정상 판정은 제한을 풀 수 없다.
12. **운행 중 재인증 (11/18 결정 D1·D2, PC 구현 후보):**
   - 시동(02)이 허용되면 차는 **시동 중** 상태가 되고 마지막 인증 시각을 기록한다. 시동 중에는 앱이 **T마다 재인증(CMD 04)**을 보낸다. 판단 순서는 1번과 같고, 오프라인이면 횟수 1을 쓴다(C 방식).
   - 재인증이 거부되거나 **T + G 동안 오지 않으면(재인증 만료)**: OLED `REAUTH` 경고를 띄우고 그 키를 **재검증 대기(07)**로 표시한다. 시동이 꺼진 뒤 다시 시동(02)을 걸면 07로 거부한다. 서버와 인증된 동기화가 되면 07을 풀고 동기화 결과를 따른다(취소면 03).
   - **달리는 중에는 시동을 끄지 않는다(안전).** 재인증 만료 뒤 **정차가 `VC_STOP_CUTOFF_S` 동안 이어지면 시동을 해제**한다. 실제 기준 600초(10분), 시연 30초. **정차 입력은 차량 쪽 신호로만 받는다**(앱·Pi 메시지로 받지 않음). 실제 차는 속도 센서, 시연은 보드 USER 버튼(B1) 토글로 주행/정차를 바꾸고 OLED에 DRIVE/STOP 표시. 웹은 상태 표시만. (앱 메시지로 받으면 공격자가 "주행 중"을 계속 보내 정차 컷오프를 피할 수 있기 때문)
   - **시동 끄기(CMD 05):** 인증은 하되 횟수를 쓰지 않고 시동 중 상태를 끝낸다.
   - CMD 04·05는 시동 권한(PERM 0x02)을 따른다(§5).
   - 값: 시연 **T=60초, G=30초**(D2). 비교 실험은 T=10·30·60분.
   - C 방식에서는 **정상 이용자도** 오프라인 재인증으로 횟수를 다 쓰면 07이 된다. 바꾸지 않고 비교 결과(정상 이용자 거부율)로 보여 준다.
   - 결과 표현: 이 규칙은 재시동과 정차 뒤 운행을 막는 것이 목표다. **정차 전까지 운행 시간 상한은 없다.**
   - 시동이 걸린 채 차가 재부팅되면 시동 중 상태는 사라지고, 재시동은 02로 다시 판단한다.

   - **구현 세부 규칙:** 차량 전체에 논리적 운행 세션 1개와 소유 KID를 둔다. 이미 시동 중인 경우 같은/다른 키의 02는 07로 거부하며 시간·횟수를 초기화하지 않는다. 04는 현재 운행 소유 키만 가능하다. 04 성공은 제어 출력을 다시 구동하지 않고 마지막 인증 시각만 갱신한다.
   - 유효 인증값·일회용 난수 확인을 통과한 소유 키의 04가 거부되면 경고/07 대기를 설정한다. 가짜 인증·재전송·다른 키 요청은 즉시 대기 상태를 만들지 않는다(정상 갱신이 없으면 시간 만료로 처리). 시간 만료는 T+G 경계 이상에서 발생한다.
   - C/D의 01·02·04는 기존 마지막 인증 동기화 기준으로 먼저 차감하고 저장한다. 온라인에도 일시 차감되지만 인증된 SYNC로 복구된다. 05는 횟수를 쓰지 않는다. 04 거부 응답은 원래 사유(예: 05)를 반환하고 이후 재시동은 07이다. H 결과를 새로 쓰지 않고 D/07로 표현한다.
   - 05는 등록·인증·난수·시동 권한·운행 소유 키 확인 후 취소/반납/만료/07/저장장애 상태에서도 허용한다. 다른 키로 남의 운행을 끄지는 못한다. 이미 꺼진 상태의 유효 시동 권한 키 05는 무동작 성공이다. 정지 경로는 새로운 Flash 저장 성공을 요구하지 않으며 07 등 저장된 제한은 지우지 않는다.
   - 대기 상태는 STATE=3으로 저장(취소/반납을 덮지 않음). 07은 02·04를 제한하며 문 열기·반납은 원래 권한/기간/횟수 판단을 따른다. 인증 SYNC에 해당 키가 유효로 명시된 경우에만 07을 풀고 횟수를 복구한다. 운행 중인 해당 키의 경고도 해제·인증 시각 갱신한다. 취소/반납 키는 되살리지 않는다. 빈 목록 SYNC만으로는 07을 풀지 않는다.
   - 경고 뒤 연속 정차 시간을 센다. 주행으로 바뀌면 정차 타이머 초기화. 초기 주행 가정(정차 미확인)에서는 자동 정지하지 않는다. USER 버튼은 부팅 모드 선택과 분리해 손을 뗀 뒤 새 누름부터 디바운스해 주행/정차 토글한다. 이는 속도 측정이 아닌 시연 가정이다. 제어 계층의 비상정지·문/잠금·HB 오류 정지는 별개로 유지한다.
   - `VC_REAUTH_ENABLE=1`, T=60/G=30초 기본, 컷오프 기본 600초. `check_arm_build.py --variant demo`는 30초·USER 토글 시연 설정이다. USER 입력 `VC_DEMO_DRIVE_INPUT`은 프로젝트 시연용이며 실제 차량에서는 끄고 로컬 센서로 sk_set_stopped를 연결해야 한다. 운행 중 여부는 논리적 판단 상태로, 모터 미사용 빌드에서 실제 시동이라고 주장하지 않는다.
   - 조회 전용 `DSTATUS` → `DSTATE|KID|RUN|WARN|STOP|ELAPSED|LEFT` 추가. KID/초 값은 8자리 hex, RUN/WARN/STOP은 0/1, OFF 세션 KID는 FFFFFFFF. 앱/Pi에서 정차 값을 쓰는 메시지는 없다. 웹은 차량 상태를 조회해 표시하고 앱 역할로 04를 주기 전송한다.
   - 시동 중 상태·타이머는 재부팅 시 초기화하지만 저장된 07은 유지한다. 운행 중 저장장애가 나도 자동으로 주행을 끄지 않고 로컬 정차 컷오프/인증 05를 따른다. 운행 중 복구 키 적용은 07로 거부한다. 보드·모터·실물 안전 검증은 미수행이다.
13. **시계 되돌림 대응 (S7, 11/28, B·D만):** 차량은 지금까지 본 가장 늦은 RTC 시각(시계 하한)을 기억한다.
   - 기간 판단(판단 순서 "기간", 복구 키의 기간 확인) 때 RTC가 시계 하한보다 **300초(`SK_CLOCK_TOLERANCE_S`) 넘게 뒤**면 시계 되돌림으로 보고 **04(기간 만료)로 거부**한다. 로그 `CLOCK ROLLBACK: period keys denied (04)`는 상태가 바뀔 때 한 번. 사유 코드·메시지 형식은 바꾸지 않는다. RTC가 하한 근처로 돌아오면 정상 판단으로 돌아간다.
   - 시계 하한은 상태를 저장할 때마다(허용된 명령, 동기화 등) 플래시에 함께 쓰고(§8 148..151), 허용된 명령이 없어도 B·D에서는 **600초(`SK_CLOCK_SAVE_STEP_S`)마다** 저장한다(하루 최대 144회). 부팅 때 저장값을 읽어 하한으로 쓴다. 저장 실패는 다른 저장과 같이 0A 복구 필요다.
   - 효과: 전원이 켜진 동안의 되돌림, 재부팅 뒤 마지막 저장 시각보다 이전으로의 되돌림을 막는다(만료 뒤 시각이 저장되면 그 키는 다시 열리지 않음).
   - **한계:** 전원이 꺼져 있던 시간은 차가 알 수 없다. 전원을 끈 시점(마지막 저장, 최대 10분 전) 근처로 RTC를 되돌리면 꺼져 있던 시간만큼 기간이 늘어난다. RTC 백업 전지가 빠져 시계가 과거로 초기화돼도 같은 거부가 일어난다(안전 쪽 실패, 정상 이용자도 04). 서버가 서명한 시각을 SYNC에 넣어 하한을 올리는 방식은 메시지 형식 변경이라 확장 과제로 둔다.
   - A·C는 시계를 쓰지 않으므로 영향이 없다. PC 시험(Python·C 같은 시나리오, 플래시 바이트 일치), 보드 실물 미수행.

### 6.2 영속 저장·복구 규칙 (2026-11-18 구현 후보)
- 최대 8키. 등록·차감·반납·재인증 대기(상태 3)·인증 동기화의 상태/VER를 함께 저장하고 완료 검증 후 성공 응답·구동한다. 같은 상태 동기화는 쓰지 않는다. 실패 시 0A로 제한하며 자동 초기화하지 않는다.
- 같은 KID 재등록은 복원한 횟수·상태 우선. 쓰다가 중단된 미완료 기록은 구동 전 저장 원칙을 전제로 제외한다. 완료 기록 손상 등 최신 상태를 확신할 수 없으면 복구 필요로 처리한다.
- 최초 설치는 서버에서 일반 키를 발급한 뒤 복구 절차로 승인한다. 무인 자동 초기화·기록 삭제 기능은 없다. 8개 초과 등록은 기존 FF 실패. 서버 목록도 동기화 형식에 맞춰 16개로 제한하며 장기 정리는 범위 밖이다.
- 복구 필요 중 KEY·REQ·RESP·SYNC로 제한을 풀지 않는다(등록된 운행 소유 키의 인증 05 정지는 예외이며 제한을 지우지 않음). 검증된 RECOVER만 새 키 1개를 저장하며 기존 키 전체를 제외한다. 복구는 새 권한 부여이므로 원래 남은 횟수 복원·복구 포함 총 사용 상한 보장이 아니다.
- PC 기존 데모는 명시적 RAM 모드(storage=None) 유지. 보드는 VC_ENABLE_FLASH=1 기본. Python/C는 같은 저장 형식·복구 메시지를 사용한다.
- 휴대폰도 통신 불가면 복구 불가, 서버가 모르는 오프라인 반납 및 발급 후 전달 전 취소는 한계. B/D 만료는 신뢰할 수 있는 시계 필요, 보드 A/C 설정은 유지한다.

### 6.1 제어 계층 규칙 (control.c, 판단 규칙과 별개)
- 부팅 시 자동 구동하지 않는다.
- 모터는 문 닫힘·잠금 확인 후 돈다. 서보는 바퀴가 멈춘 상태에서 움직인다.
- 모터 구동 중 문·잠금 입력이 사라지거나, 생존 신호가 2초 끊기거나, 서보가 시간 안에 끝점에 못 가면 정지하고 오류를 유지한다.
- **다시 잠그기 (11/1 결정):** 문열기(01) 허용으로 잠금이 풀린 뒤, 문 닫힘 스위치(PF12)가 **열림 → 닫힘**으로 바뀌면 서보를 잠금 위치로 돌린다. 메시지 형식·판단 규칙은 바꾸지 않는다(제어 계층 동작). **11/5 판정: 사용.** 김채희 11/4 실물(§9): 온라인 5회 연속 해제↔잠금, Pi 경유 오프라인 C를 다시 잠그기까지 오류 없이 1회. 문짝 부착 뒤 10회 반복은 남음. (이전: 11/2 곽동규 구현·PC 시험, "중간발표 전 구현" 결정)
  - 구현: v2 `vehicle_app.c`에서 디바운스된 문 닫힘 에지 → `ACT_LOCK`. 설정 `VC_RELOCK_ON_DOOR_CLOSE`(기본 1, 0이면 이전 동작). 기존 안전 조건(문 닫힘 상태에서만 잠금, HB 유지, 오류 시 구동 안 함) 유지
  - 조건: 활성(armed)·오류 없음·**UNLOCKED 상태**일 때만. 부팅 후 첫 디바운스 값은 기준값이라 동작하지 않는다. 막힌 닫힘 에지는 버리고 나중에 다시 시도하지 않는다
  - **위치 UNKNOWN(부팅 직후)에서는 잠그지 않는다** (11/3 확정). 부팅 후 첫 허용으로 해제된 뒤부터 동작한다
  - 잠그는 중 문이 열리면 기존대로 FAULT_DOOR(오류 유지). 잠금은 키 횟수를 차감·복구하지 않는다
  - **조작 규칙 (11/4 곽동규·김채희):** 다시 잠그기는 스위치의 **열림→닫힘 변화**로만 일어난다. 처음부터 계속 눌러 두면 잠그지 않는다. 매회 "해제 끝 → 스위치 뗌 → 다시 누름 → 잠금 끝(0.5초 이상)까지 눌린 채 유지". 잠그는 중 떨어지면 FAULT_DOOR → RESET·재등록. 문짝은 **열면 스위치가 떨어지고 닫으면 계속 눌리는 구조**로 만든다(자석 또는 케이스 걸쇠)
  - (이전 조건 "11/5까지 안 되면 첫 해제만"은 판정으로 해소)
- 서보 잠금/해제 **2000/1200μs 확정** (D9, 11/17. 김채희 보드판 `_v6`·`_v7` 실물 확인값, 시험 시각·횟수 미상. 11/6 곽동규 보정값 900/2100μs는 쓰지 않음). 50Hz
- 임시값(실물에서 보정): 모터 PWM 10kHz·상한 60%, 디바운스 30ms, 서보 제한 1.5초

  - **추천 (02 §7.2 규칙, 2-1 평균 규칙은 결과를 본 뒤 11/19 추가):** 정상 이용자 거부율 5% 이하를 지키는 방식은 A·B·D-현실(무제한·20회)이고, 그중 취소 뒤 평균 사용이 가장 작은 것은 **B(= D-현실 무제한·20회, M=0)**다. 즉 "결제한 기간 안은 막지 않고, 기간이 끝나면 바로 막는다". 기준을 10%로 넓히면 D-현실(24시간, M=0)이 추천된다. B는 차량 시계(RTC)가 필요하다. 시계 되돌림(S7)은 11/28 시계 하한 규칙(§6 13)으로 대응했고(PC 시험), 전원을 꺼 둔 시간만큼은 막지 못한다.
  - **오프라인 중 취소된 키 시도를 막은 비율 (상황 1, 11/28 추가, `recommend.md`):** A 0.0%(0/157), B 43.9%(69/157), C(N=4) 50.3%, D(N=4) 70.1%, D-현실(24시간, M=0) 62.4%. B가 막은 69번은 모두 대여 기간이 끝난 뒤의 시도이고(69/69), 허용한 88번은 모두 기간 안의 시도다. 온라인 시도는 모든 방식이 03으로 거부하므로 뺐다. 11/26까지 말로 쓰던 "B 71%"는 온라인 시도를 포함한 값이라 이 값으로 바꾼다.

### 내부 플래시 저장 형식·적용 (2026-11-18 구현 후보)
- 섹터 22(0x081C0000), 23(0x081E0000), 각 128KiB. 프로그램 FLASH 길이 1792K로 제한. 저장 드라이버는 실제 load image가 bank 1 안(0x08100000 이하)에 있는지도 검사한다. 보드 설정 대조·실물 검증은 미수행이다.
- 256바이트 기록: 0..3 `SKJ1`, 4 형식=1, 5 종류(0 상태/1 복구 장벽), 8..11 순번, 12..15 VID, 16..19 VER, 20..147 키 8슬롯(각 16B), 148..151 시계 하한(유닉스 초, 0 없음, 11/28 추가 — 이전 기록은 FF라 0으로 읽음), 248..251 CRC32(0..247), 252..255 완료=0. 정수 big endian, 예약 FF(빈 키 슬롯은 0).
- 키 슬롯: KID(4), EXP(4), LIMIT(1), REMAINING(1), SIT(1), PERM(1), STATE(1), USED(1), 예약(2). 상태 0 유효/1 취소/2 반납/3 재검증 대기(이전 펌웨어와 3 상태 복원 호환 안 됨). C 구조체 직접 덤프 금지.
- 본문 기록·읽기 검증 후 완료 워드를 마지막에 쓴다. 새 구역의 기록 완료 전 현재 구역을 지우지 않는다. 부팅 때 양쪽 구역 전체를 검사한다. CRC가 틀린 완료 기록은 과거 기록으로 조용히 되돌리지 않고 복구 필요로 처리한다.
- 복구는 손상 기록을 보존한 채 반대 구역에 더 높은 순번의 복구 장벽을 기록한다. 기존 구역을 지우고 장벽보다 높은 새 상태를 기록한다. 장벽만 있으면 사용 불가. 재시도 시 기존 장벽을 보존한 채 반대 구역에 새 상태를 기록한 뒤 장벽 구역을 지운다.
- 순번 소진·I/O 실패는 제한한다. 지우기는 모터·서보 동작 중 거부한다. HAL 지우기는 foreground를 지연시키므로 최악 지연·통신·watchdog 영향은 실물 확인이 필요하다. 전압 조건은 3.3V 보드 기준이며 전압 저하 내성은 미검증이다.
- 최초 빈 저장소도 복구 필요다. 전체 업로드 삭제 시 저장 데이터도 사라진다. 물리적 변조·과거 이미지 복원·완료 마커 자체 소실 등 모든 손상을 검출한다고 주장하지 않는다.

## 12. 개발 규칙
0. 요청 범위 안의 구현 선택과 설계 변경은 작업 브랜치에서 자율적으로 진행하고 이 문서·코드·PR에 이유와 결과를 반영한다. 별도 팀장·팀원 승인 대기는 두지 않는다. 요구사항이 불명확하면 필요한 질문을 한다.
1. AI는 이 문서와 AGENTS.md를 먼저 읽고 작업 브랜치 생성 → 수정 → 검증 → Commit → 작업 브랜치 Push → PR까지 별도 허락 없이 진행한다. 설계 변경이 필요하면 요청 범위 안에서 같은 브랜치의 문서와 코드를 맞춘다. 사용자가 로컬 작업만 요청하면 해당 범위에서 멈춘다.
2. 작업이 끝나면 **코드와 함께 작업 보고**를 남긴다. 보고는 별도 작업 MD 대신 **GitHub PR 본문**에 01 양식(`docs/01_report_template.md`, `.github/pull_request_template.md`)으로 쓴다. 코드만 올리지 않는다. 별도 MD는 사람이 요청할 때만 만든다. (v0.3.13 전: 작업 MD를 팀장에게 전달)
3. 메시지 형식, 판단 순서, 사유 코드를 바꾸면 Python(core.py)과 C(sharekey.c)를 **둘 다** 고치고, `demo.py --relay-c` 결과가 같은지 확인한다. (Python 코드가 저장소에 들어오기 전까지는 C와 `firmware/stm32` 호스트 시험만 해당, §9 저장소 기준)
4. 디버깅은 로그로 한다. 시리얼 로그를 복사해 AI에게 주고, 필요한 로그를 추가해 다시 돌린다.
5. 하드웨어 핀은 사진을 찍어 AI에게 확인받되, 결과는 §8 핀표에 반영한다.
6. 코드와 문서는 GitHub 저장소 하나에서 관리한다. 일 하나에 브랜치 하나, main에 직접 커밋·Push하지 않는다. 필요한 검증 뒤 대상 PR·최신 변경·검증 결과를 사용자에게 보여 주고 **main 최종 병합 허락을 받은 경우에만** 합친다. 팀원 리뷰·승인은 필수가 아니며 자동 병합·예약은 하지 않는다(자세한 규칙은 AGENTS.md).

### 15.2 시연 (부스 책상)
- 구성: 노트북 **웹 화면(`web_app.py`, 11/4 차량 앱 형태로 개편)** + 차 모양 모듈(4WD **아래판**에 보드·건전지(밑면)·OLED, 문짝 = **다이소 투명 경첩 케이스 뚜껑**(11/5, 우드락 대신) + 서보 걸쇠 + 택트 스위치(닫히면 계속 눌림, 걸쇠·자석), Pi는 차 옆) + Pi 5. 화면은 노트북을 그대로 보여 준다
- **A·C 모두 현장 실물:** 보드 1개에서 **USER 버튼으로 방식 전환** — 그냥 RESET = C, USER 누른 채 RESET 후 손 떼기 = A (후보판 `stm32_vehicle_control_f429_v2_1103`, 발표용 빌드에서 `VC_DEMO_MODE_SELECT 1`). RESET하면 키가 지워지므로 전환 후 등록부터
- **A 영상은 예비용**(버튼 전환이나 보드에 문제가 있을 때)
- **반복 시연:** 방문자마다 서버를 다시 켜지 말고 **공유 키 번호만 바꿔** 발급·등록(7, 8, 9…). 한 번에 1~2분: 등록 → 문 열기(+문 닫기) → 2초 이상 뒤 **차량 오프라인** → 몇 초 뒤 취소 → 문 열기 6번 → **차량 온라인** → 몇 초 뒤 문 열기(03)
- 다시 잠그기(§6.1, 11/5 사용 확정): 허용되면 걸쇠가 풀리고 사람이 문을 열었다 닫으면 잠긴다. 거부되면 걸쇠가 그대로라 당겨도 안 열린다. **문은 매번 실제로 열었다 닫아야** 다시 잠근다(스위치 변화). OLED가 멈추면 5~10초 대기 → 보드 RESET → OLED 전원 재투입 순서로 풀고 몇 번째에서 풀렸는지 기록
- **IP 규칙 (11/6 김채희 정리):** Pi에서 `pi_relay.py --server <노트북 IP>`, 노트북에서 `web_app.py --vehicle <Pi IP>`. 문 3D 표시는 Pi의 9101 포트(§5)를 읽으므로 같은 Pi IP를 쓴다(`--door`로 따로 줄 수 있음). 장소가 바뀌면 두 IP를 다시 확인
- 처음 켜는 순서: 서버(상태 초기화) → Pi 중계 → 보드 RESET → 웹 화면. 서버·중계를 다시 켜면 보드 RESET. 전원: 켤 때 USB → 건전지, 끌 때 건전지 → USB
- **현장 콘센트 확인**(Pi USB-C 전원, 노트북). 없으면 보조배터리

### 15.3 표현·표기
- 제목: 취소해도 남는 공유 차 키 — 오프라인 차량을 위한 차량 측 사용 제한 모듈 설계
- 기능 블록도에서 노트북–Pi 연결은 빨간 점선 "실험 시 차단", STM32는 "최종 판단"으로 강조. 제안 발표의 블록도·흐름도·일정 그림 재사용
- 예시 데이터는 정답표 값 사용 (공유 키 번호 7 등). 청중용 화면·포스터에서는 KID 대신 "공유 키 번호", 서버 끊기·연결은 **"차량 오프라인/차량 온라인"**(예: 지하주차장, 오래 시동을 걸지 않아 통신이 멈춘 경우 — §1 블루링크 48~336h). 시연 버튼은 서버의 동기화 응답 중단(`app.py net off`)이며 실제 장시간 주차를 재현한 것이 아니다
- 측정하지 않은 목표를 결과처럼 쓰지 않는다. 실물 결과는 각 1회 시행으로 표시하고, 서보·저장 등 확인 안 한 기능은 완료로 쓰지 않는다. 보드는 NUCLEO-F429ZI로 표기
- 쓰지 않는 말: "오프라인 취소 탐지", "성능 목표 달성", "재부팅해도 유지", "시동 구현"(판단만, 모터 꺼짐), C를 우리 아이디어로 소개(기존 방식, 비교 대상), **"피해 상한 보장"**(재부팅 재등록 구멍이 남아 있음 — "재부팅당 상한"으로)
- 한계는 먼저 말한다: 마스터키 개발용 고정값, 메시지 암호화 없음, 키 RAM 저장(재부팅 재등록), 근접성 검증 범위 밖
- 발음: UART=유아트, STM32=에스티엠 삼십이, HMAC=에이치맥, nonce=논스
- 참고문헌: [1]~[10] 설계 문서 순서 + [11] 현대 블루링크 원격 도어 제어 안내 + [12] 지도교수 자료(디지털 키 보안 연구 제안, 2026-10-01 기준) §2.4 + [13] 비즈한국 2022-04-15 그린카 서버 마비·쏘카 블루투스 스마트키
- 예상 질문 담당: 보안 = 권기백, STM32·하드웨어 = 곽동규, Pi·AI = 김채희, 센서·모터 = 조민선
