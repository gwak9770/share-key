## 3. 운행 중 재인증 (S3·L4·L5) — 설계 (D1·D2 확정 11/18)

### 3.1 문제
지금 횟수는 **시동 횟수**다. 시동을 한 번 걸고 끄지 않으면 통신을 끊은 채 무제한 운행할 수 있다(S3 → L4 추적 회피 운행 → L5 도난·반출).

### 3.2 규칙 (11/18 확정)
1. 시동(CMD 02)이 허용되면 차는 **시동 중** 상태가 되고 `last_auth` 시각을 기록한다.
2. 시동 중에는 앱이 **T마다 재인증(CMD 04)**을 보낸다. 흐름은 기존과 같다: `REQ|KID|04` → `CHAL` → `RESP` → `RES`.
3. 재인증 판단은 시동(02)과 **같은 순서**(등록 → 인증값 → nonce → 취소/반납 → 기간 → 권한 → 횟수)로 하고, **오프라인이면 횟수 1을 쓴다.** C 방식에서는 정상 이용자도 재인증으로 횟수를 다 쓰면 07이 된다. 바꾸지 않고 비교 결과(정상 이용자 거부율)로 보여 준다.
4. 재인증이 거부되거나 **T + G 동안 오지 않으면(재인증 만료)**:
   - **달리는 중에는 시동을 끄지 않는다** (안전).
   - OLED에 `REAUTH` 경고를 띄운다.
   - 그 키를 **재검증 대기(사유 07)**로 표시한다. 시동이 꺼진 뒤 다시 시동(02)을 걸면 07로 거부한다.
   - 재인증 만료 뒤 **정차가 `VC_STOP_CUTOFF_S`(실제 600초 = 10분, 시연 30초) 동안 이어지면 시동을 해제**한다.
   - 정차 입력은 차량 쪽 신호로만 받는다(앱·Pi 메시지로 받지 않음). 실제 차는 속도 센서, 시연은 보드 USER 버튼(B1) 토글로 주행/정차를 바꾸고 OLED에 DRIVE/STOP 표시. 웹은 상태 표시만. 앱 메시지로 받으면 공격자가 "주행 중"을 계속 보내 정차 컷오프를 피할 수 있기 때문이다.
   - 서버와 인증된 동기화가 되면 07을 풀고 동기화 결과를 따른다(취소면 03).
   - 결과 표현: **정차 전까지 운행 시간 상한 없음.** 막는 것은 재시동과 정차 뒤 운행이다.
5. **시동 끄기(CMD 05):** 인증은 하되 횟수를 쓰지 않는다. 시동 중 상태를 끝낸다.
6. 시동이 걸린 채 차가 재부팅되면 시동 중 상태는 사라진다. 재시동은 02로 다시 판단한다(플래시 저장 대상 아님).
7. CMD 04·05는 **시동 권한(PERM 0x02)**을 따른다. KEY 형식·PERM 비트는 바꾸지 않는다.

## 4. 플래시 저장 (S4·T04) — 설계 (D5 확정 11/18)

### 4.1 문제
키 기록이 RAM에만 있어 재부팅 뒤 같은 키를 재등록하면 횟수가 다시 채워진다(00 §6 7-1). 지금의 상한은 "재부팅당 상한"이다.

### 4.2 저장할 것
| 항목 | 크기 | 비고 |
|---|---|---|
| KID | 4B | |
| 남은 횟수 | 1B | |
| 상태 | 1B | 0 유효 / 1 취소 / 2 반납 / 3 재검증 대기(07) |
| EXP, LIMIT, PERM | 6B | 재등록 비교용 |
| 동기화 VER | 4B (전체 1개) | 옛 목록으로 되돌리기 방지 |
| 기록 번호, CRC | 4B | 마지막 기록 찾기, 깨짐 확인 |

### 4.3 규칙 (제안)
1. 순서는 00 §6 3번 그대로: **횟수 차감 → 플래시 기록 → 구동.** 기록이 실패하면 구동하지 않는다.
2. 섹터 22·23을 번갈아 쓴다. 기록은 이어 쓰고, 한 섹터가 차면 최신 값만 다른 섹터로 옮긴 뒤 지운다.
3. 부팅 때 두 섹터를 읽어 CRC가 맞는 최신 기록으로 키 표를 복원한다.
4. 같은 KID를 재등록하면 **저장된 남은 횟수와 상태를 유지한다**(00 §6 7번이 재부팅 뒤에도 적용됨).
5. 링커 스크립트(`build_support/stm32f429zi.ld`와 CubeIDE 프로젝트의 `.ld`)에서 FLASH 길이를 1792K로 줄여 코드가 섹터 22·23을 쓰지 않게 한다. 저장소 `.ld`는 곽동규, CubeIDE `.ld`는 김채희가 바꾼다(11/18 결정).
6. 섹터 정리(지우기)는 1~2초 걸릴 수 있으므로 **모터가 멈춘 상태에서만** 한다. 00 §6.1의 생존 신호 2초 정지 규칙과 겹치지 않게 하기 위해서다(11/18 결정).

## 5. 비교 실험 (T06·F2·F8) — 설계

### 5.1 비교할 방식
| 방식 | 설정 |
|---|---|
| A | 서버 취소만 |
| B | 대여 기간(EXP)만 |

## 7. 추천 규칙 (최종 결론)

### 7.1 공유 유형
| 유형 | 조건 범위 |
|---|---|
| 단기 카셰어링 | 대여 30분~6시간, 결제형 |
| 장기 렌터카 | 대여 1~3일 |
| 지인·가족 공유 | 기간 없음(또는 30일), 무료 |
| 지하 주차가 잦은 곳 | 오프라인 길이 상위 25% |

각 유형은 §5.3 조건 중 해당 범위만 골라 계산한다.

### 7.2 규칙 (실험 전에 확정)
1. 정상 이용자 거부율 **5% 이하**(00 §7 초기 기준)인 방식만 남긴다.
2. 그중 **취소 뒤 최대 사용**(①)이 가장 작은 방식을 추천한다.
3. 같으면 재부팅 견고성(④) → 통신량(③) 순서로 고른다.
4. 남는 방식이 없으면 "이 유형은 거부율 5%로는 막을 수 없음"이라고 쓰고, 거부율이 가장 낮은 방식을 참고로 적는다.
5. **민감도:** 기준을 10%로 바꿔도 추천이 같은지 표시한다.

### 7.3 결과물
`docs/results/recommend.md`: 유형 × (추천 방식, ①, ②, 기준 10%일 때 추천) 표. 발표에서는 이 표와 손익 그래프(가로 ② 거부율, 세로 ① 취소 뒤 사용)를 보여 준다.

## 12. 이 문서 쓰는 법

- 할 일을 시작할 때 이 문서의 해당 절을 Claude Code에 그대로 알려 준다. 예: "02 로드맵 §4 플래시 저장 2단계를 해 줘."
- 끝나면 PR 본문에 "02 로드맵 §○ ○단계 완료"라고 적고, 이 문서의 상태 칸(§1)과 날짜를 같은 PR에서 바꾼다.
- 결정(§2)이 바뀌면 00을 먼저 고치고, 이 문서의 해당 설계안을 "확정"으로 바꾼다.
- 마감이 밀리면 이 문서의 날짜를 고치고 단톡방에 알린다.
