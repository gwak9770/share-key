## 1. 한 일 (요약 3줄 이내)
- 어제 HardFault의 원인이 **보드 모델 차이**였음을 찾았다. 실물 보드는 **NUCLEO-F429ZI**인데 프로젝트는 F767ZI용이었다. F429ZI용 새 프로젝트로 다시 빌드해 `# boot`, `SYNCREQ`, `KEYOK`을 확인했다.
- 노트북을 Pi 대신 써서(COM4) 실물 보드로 A·C 시연을 했다. 이어 **Pi 5 + 실물 보드**(00 §3 구조 전체)로 A·C 시연을 했다.
- 두 경로 모두 취소 후 추가 사용 **A 6/6, C 4/6**, 변조 01, 재전송 02, 동기화 후 03이 나왔다(각 1회 시행). 보드는 C로 되돌렸고, 00 §8 핀표가 F429ZI에서 쓸 수 있는지 CubeMX로 대조했다. F429ZI 확정, 서보 시험은 전원(4구 홀더) 문제로 다음으로 미룸.

## 4. 전체 설계와 다른 점 (중요)
- **보드 모델:** 00 §3·§8·§9는 NUCLEO-F767ZI, 실물은 **NUCLEO-F429ZI**. 오늘 시험은 모두 F429ZI로 했다.
- **변경 요청 (보드는 14:36 확정. 00·공유 코드는 직접 안 고침, 문서 관리자가 반영)**
  | 위치 | 바꿀 내용 |
  |---|---|
  | 00 §3, §8 | NUCLEO-F767ZI → NUCLEO-F429ZI |
  | 00 §9 | STM32CubeF7 1.17.4 → **STM32CubeF4 1.28.3** (CubeIDE 1.19.0은 그대로) |
  | 00 §13 | 위 변경 기록. "ETH·USB_OTG_FS 안내는 HardFault 원인 확인 후"는 원인이 보드 모델로 확인됨 → ETH·USB 끄기는 원인이 아니었음. 꺼 둔 것은 00에 없는 기능이라 그대로 둬도 됨 |
  | README_STM32 [2] | 보드 NUCLEO-F429ZI, 패키지 STM32CubeF4, "ETH·USB_OTG_FS는 Disable(00에 없는 기능)" |
  | port_stm32.c 맨 위 주석 | "NUCLEO-F767ZI" → F429ZI (주석만. 코드는 수정 없이 동작함을 오늘 확인) |
  | 설계 문서·발표 PPT | F767 표기가 있으면 F429로 |
- **핀:** USART3 = PD8 TX / PD9 RX는 F429ZI 보드 기본 설정에서도 같음을 CubeMX로 확인했다. LD1(PB0)·LD3(PB14)은 허용·거부 때 켜지는 것을 실물로 봤다. 나머지 핀은 CubeMX에서 **00 §8의 기능을 고를 수 있음**을 확인했다(§5 핀 대조). 보드 회로에서 다른 부품과 연결돼 있는지는 보드 매뉴얼(UM1974)로 아직 확인하지 않았다.
- **클록:** F429 기본 설정 = SYSCLK 168MHz(PLL, HSE 8MHz), 48MHz clocks = 48 → 00 C8(PLL로 RNG 48MHz)과 맞음.
- **환경:** 오늘 서버·앱은 Windows(Python 3.13)에서 실행. 00 §8의 노트북(macOS) 기준과 다르지만, 확인한 명령 범위에서는 정상 동작.
- **전원 부품:** 지금 있는 건전지 홀더는 **6구**뿐. 00 §8은 AA 4개(6V). 6개(9V)로 쓰면 서보·TT 모터 허용 전압 초과 → 4구 홀더 필요 (§6)
- 메시지 형식·판단 규칙·사유 코드·파일 구조 변경: **없음**.

## 7. 다음에 할 일

3. **서보 단독 시험**: 새 시험 프로젝트 `servo_test_f429`(sharekey_f429·공유 코드와 분리)에서 PD14 TIM4_CH3 50Hz PWM, 1200↔1800μs 왕복 (00 §6.1 임시값). 프로젝트 생성·빌드는 전원 없이 먼저 가능
4. 곽동규에게 `stm32_vehicle_control_v1/` 받기 → F4 빌드 가능 여부 확인 → 조민선 서보 코드와 함께 `sharekey_f429`에 통합 (10/29~30 일정)
5. 핀: CubeMX 대조는 끝남(§5). 이상하면 보드 매뉴얼(UM1974)로 회로 연결 확인
6. 발표용 캡처 다시 찍기: Pi 경로 A·C 시나리오를 앱 창 처음(issue)부터 끝까지 한 장씩 (오늘 캡처는 앞부분 잘림)
7. 발표 질의응답(Pi·AI 담당) 준비
8. 나중 영향: 내부 플래시 저장(11/16)은 F429 플래시 섹터 배치 기준으로 설계 (F767과 다름)

## 8. 참고 (사용한 자료, AI 대화에서 나온 중요한 내용)
- 기준: 00_master_design.md v0.3.1, README_STM32.txt, hardfault_check_1027.md(권기백), 권기백_보드준비_문서관리_1027.md, 곽동규_라즈베리파이세팅_1028.md
- HardFault 원인 근거: F767 프로젝트 링커의 스택 시작 `_estack`은 0x20080000(F767 RAM 512KB 끝). F429ZI 일반 SRAM은 0x20000000~0x2002FFFF(192KB)라 그 주소가 없음 → 부팅 직후 스택 쓰기 실패, 어제 Fault Analyzer의 IMPRECISERR + STKERR와 맞음. F429 프로젝트로 바꾸자 정상 동작해서 원인으로 판단
- NUCLEO-F429ZI는 ST 목록에 "Obsolete"(신규 판매 종료) 표시. 개발·사용에는 영향 없음
- Windows 실행 메모
  - 새 PowerShell 창은 `C:\Users\user`에서 열림 → 먼저 `cd "<sharekey 폴더>"`
  - 상태 초기화: `Remove-Item -Recurse -Force server_state.json, keys -ErrorAction SilentlyContinue`
  - 시리얼: `python -m serial.tools.miniterm COM4 115200 --echo` (끄기 Ctrl+]). pi_relay가 COM4를 쓰려면 miniterm을 꺼야 함
  - Pi 연결 시 앱 명령 끝에 `--vehicle <Pi IP>:9100`, Pi는 `--server <노트북 IP>:9000`. IP는 `ipconfig` / `hostname -I`로 매번 확인
- 온라인 중 open 후 남은횟수가 다시 4로 보이는 것: 2초마다 인증된 동기화로 복구됨(00 §6-4)
- 보드는 서버 연결 전까지 2초마다 SYNCREQ를 계속 보냄(정상). RESET 없이도 업로드 후 바로 실행됨
- CubeIDE에서 Run As 메뉴로 올릴 것(그냥 ▶는 이전 프로젝트 설정으로 실행될 수 있음)
- 비밀번호·Wi-Fi 정보는 기록하지 않음
