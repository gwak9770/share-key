# 김채희 중간 공유 — 보드 모델이 00 문서와 다름 (HardFault 유력 원인)

> 2026-10-28 · 기준 문서 00_master_design.md **v0.3.1** · 받는 사람: 권기백(결정), 곽동규(참고)

## 발견한 것 (사진으로 확인)
- 우리가 쓰는 보드 실크 인쇄: **NUCLEO-F429ZI** (MB1137 Rev B)
- 칩 각인: **STM32F429ZIT6U** (Cortex-M4)
- 00 §3·§8·§9와 CubeIDE 프로젝트는 **NUCLEO-F767ZI**(Cortex-M7) 기준. 어제 프로젝트도 F767ZI로 만들어 F429 보드에 올렸음.

## HardFault와의 관계 (추정, 확인 전)
- F767 프로젝트 링커 설정은 스택 시작(`_estack`)이 RAM 끝 **0x20080000**(F767 RAM 512KB 기준).
- F429ZI 일반 SRAM은 **0x20000000~0x2002FFFF**(192KB)라 0x20080000은 없는 주소.
- 부팅 직후 첫 스택 쓰기부터 실패 → 어제 Fault Analyzer의 **IMPRECISERR + STKERR**, `# boot` 출력 없음과 맞음.
- ETH·USB를 꺼도 해결 안 된 것과도 맞음. (오늘 Clean 빌드 0 errors, 업로드 성공까지 확인. 시리얼 결과는 이 발견으로 보류)

## 결정 요청 (권기백)
1. 팀에 **NUCLEO-F767ZI 실물이 따로 있는지** 확인 (누가 갖고 있는지)
2. 없으면 **NUCLEO-F429ZI로 진행**할지 결정. 그 경우 00 수정 필요:
   - §3·§8 보드명, §9 펌웨어 패키지(STM32CubeF7 → **STM32CubeF4**), README_STM32 [2] 보드 선택
   - 핀(USART3 PD8/PD9, LED PB0/PB7/PB14 등)은 같은 Nucleo-144 계열이라 같을 것으로 보이나 **보드 매뉴얼 대조 필요**
   - 동규 제어 코드(TIM1 모터, 서보 PD14, I2C1)도 F4에서 확인 필요
3. 공유 코드(sharekey.c, sk_crypto.c, port_stm32.c)는 보드 무관 C + HAL 이름(huart3, hrng)만 써서 **수정 없이 쓸 수 있을 것으로 보임** (확인 전)

## 결과 (13:11 추가) — HardFault 해결 확인
- NUCLEO-F429ZI 새 프로젝트 `sharekey_f429`(CubeIDE 1.19.0 + **STM32CubeF4 1.28.3**)로 빌드 0 errors, 업로드 성공
- 설정: USART3 115200 8N1 + 인터럽트(PD8 TX / PD9 RX), RNG Activated, ETH·USB_OTG_FS Disable, SYSCLK 168MHz(PLL), **48MHz clocks = 48**
- 시리얼(COM4) 출력 **정상**: `# boot`(앞부분은 연결 전이라 `ot`만 보임), 2초마다 `RID|SYNCREQ|0000CAFE|NONCE|00000000`, RID·NONCE 매번 다름, `# no server response -> OFFLINE`
- → **보드 모델(F767 프로젝트를 F429 보드에 올림)이 HardFault 원인이었던 것으로 판단** (ETH 끈 F767 프로젝트는 계속 HardFault, F429 프로젝트는 정상)
- **KEYOK 확인 (13:15)**: README_STM32 [3]의 정답표 KEY 줄을 miniterm으로 보냄 → `# KEY ok kid=00000007 limit=4`, `01|KEYOK|00000007` 수신. **보드의 KEY 인증값(HMAC) 검증이 hmac_vectors.txt와 일치**
- **실물 보드 C 방식(N=4) 시연 성공 (13:18~13:25)**: 노트북 1대에서 `server.py` + `pi_relay.py --serial COM4`(노트북이 Pi 역할) + `app.py`, 보드는 NUCLEO-F429ZI(`sk_init('C')`)
  | 요청 | 앱 결과 | 보드 로그 |
  |---|---|---|
  | 동기화 | — | `server sync ok -> ONLINE`, `SYNC applied ver 0 -> 1` |
  | register 7 | 등록 성공 | `KEY ok kid=00000007 limit=4` |
  | open 7 (온라인, 3회) | 허용(00), 남은횟수 3 (동기화로 매번 4 복구) | 초록 LED(LD1) 1초 |
  | tamper 7 | 거부 **01** 인증값 불일치 | `DENY ... reason=01`, 빨간 LED(LD3) |
  | replay 7 | 거부 **02** nonce 재사용 | `DENY ... reason=02`, 빨간 LED |
  | net off → revoke 7 → open 7 ×6 | 1~4회 **허용**(남은 3→2→1→0), 5·6회 거부 **05** | `no server response -> OFFLINE`, `DENY ... reason=05` ×2 |
  | net on → open 7 | 거부 **03** 취소된 키 | `SYNC applied ver 1 -> 2`, `ONLINE`, `DENY ... reason=03` |
  - **취소 후 추가 사용: C 4/6회** — 00 §9의 PC 결과(C 4/6)와 같음 (실물 1회 시행)
  - **A 방식 실물 시연 (13:30~13:32)**: 김채희 프로젝트의 port_stm32.c **복사본만** `sk_init('A')`로 바꿔 빌드·업로드 (공유 원본은 안 고침, 시험 후 'C'로 되돌림). 같은 순서로 실행
    - open: 허용(00), 남은횟수 **제한없음** / tamper **01** / replay **02**
    - net off → revoke 7 → open 7 ×6: **6회 모두 허용**
    - net on → open 7: 거부 **03** (`SYNC applied ver 1 -> 2` 뒤)
  - **실물 결과 표 (각 1회 시행)**: 취소 후 추가 사용 **A 6/6, C 4/6** — 00 §9 PC 결과와 같음
  - 이번 시험 중 잘린 줄·형식 오류 로그는 안 보였음
- 관찰: 줄 앞에 공백이 붙으면(`   01|KEY|...`) RID가 2글자가 아니라서 **아무 응답 없이 무시됨** (sharekey.c `sk_handle_line` 동작대로). 시험할 때 줄 앞 공백 주의. 공유 코드는 안 고침
- 관찰: 약 15줄 중 1줄이 중간이 잘려 다음 줄과 붙어 나옴 (`C9|SYNCREQ|0000CAFE|43A6B|SYNCREQ|...`). 원인 미확인(보드 송신·ST-LINK VCP·PC 쪽 중 어디인지 모름). 계속 관찰

## 진행 상황
- 김채희: 보드 실물이 F429ZI뿐이라 **F429ZI로 진행**하기로 하고, 노트북에서 **새 프로젝트 `sharekey_f429`**(STM32CubeF4) 시험 시작. 같은 설정(USART3 115200 8N1+인터럽트, RNG 48MHz, ETH·USB 끔)으로 `# boot` / `SYNCREQ` / `KEYOK` 확인 예정
- 기존 `sharekey_f767` 프로젝트는 지우지 않고 보관
- 00·공유 코드는 고치지 않음 → 아래는 **변경 요청**
