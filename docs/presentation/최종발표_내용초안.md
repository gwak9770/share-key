# 최종발표 내용 초안 (12/7)

> 작성: 권기백 · 2026-11-28 · 기준: 00 v0.3.28 §1.1(최종 결론)·§1.2·§2.1·§7, 02 §9(시연 구성)
> 용도: 조민선이 슬라이드·포스터로 옮길 **내용**. 디자인·분량은 발표 형식 공지(02 §8 "확인 필요")에 맞춰 조정한다.
> 표기 규칙(00 §15.3): 숫자마다 **PC 모의 / PC 시험 / 실물 n회 / 계산값**을 붙인다. 실물이 아닌 것을 실물처럼 쓰지 않는다.

---

## 이야기 순서 (한 줄씩)

1. 공유 차 키는 취소돼도, **차가 오프라인이면 취소를 모른다.**
2. 오프라인은 공격자가 **만들 수 있다.** 그러면 무단 사용에서 **차량 도난**까지 이어진다.
3. 서버 취소만 하는 지금 방식은 **오프라인 중 시도를 하나도 막지 못한다.**
4. 우리 모듈은 차가 **스스로** 기간 끝난 키를 거부하고, 끌고 가던 차는 **정차 뒤 다시 출발하지 못하게** 하는 것이 목표다.
5. 정상 고객은 **한 번도 막지 않는다.** 그래서 카셰어링 회사가 쓸 수 있다.

## 슬라이드별 내용

### 1. 제목
- **취소해도 남는 공유 차 키 — 오프라인 차량을 위한 차량 측 사용 제한 모듈**
- 부제: "끊긴 차도 스스로 지키는 공유 키"
- 팀원·조 번호(발표 당일 번호), 영남대 소프트웨어프로젝트

### 2. 문제: 취소가 차에 닿지 않는 순간이 있다
- 카셰어링 앱에서 대여를 취소하거나 반납하면 **서버**는 키를 지운다. 그런데 차가 서버와 끊겨 있으면 **차는 그 사실을 모른다.**
- 실제로 있는 경로: 쏘카 차량 단말은 서버 명령과 **블루투스 명령을 둘 다** 받는다(쏘카 기술 블로그 2026-01-08). 2023-05-25 KT 장애 때 쏘카는 **블루투스로 문을 여는 방법**을 직접 안내했다(쏘카 공지).
- 그림: 휴대폰 —(블루투스)— 차 ✕ 서버

### 3. 공격자는 오프라인을 만든다 — 어디까지 가나
- 오프라인 만들기: 지하주차장, 안테나·퓨즈 분리, 전파 차단 가방
- 공격 사슬 (00 §1.2): **L1 무단 사용 → L2 다음 이용자 짐 절도 → L3 무면허·뺑소니 → L4 통신 끊고 계속 운행 → L5 도난·해외 반출**
- 실제 사례 한 줄씩: 테슬라 렌터카 — 반납 후 인증이 지워졌는데도 다시 열고 시동, GPS 끄려 함(CarAdvice) / 카셰어링 명의 도용 무면허 뺑소니(뉴스토마토 2017) / Car2Go 시카고 100대 도난(VICE)

### 4. 지금 방식은 뚫린다
- **방식 A(서버 취소만):** 취소된 키로 오프라인 중 시도한 **157번 중 막은 것 0번** (PC 모의, 조건 28개)
- 즉 L1~L5가 모두 열려 있다. 통신이 다시 연결될 때까지 차는 계속 열린다.

### 5. 우리 모듈 — 차가 스스로 판단한다
- 구조 그림: 앱(휴대폰) → Pi 5 중계(전달만) → **STM32 보드(판단은 여기서만)** → 서보(문 잠금)·모터(시동)·OLED
- 판단 규칙 5개
  1. **대여 기간 확인 (방식 B):** 결제한 기간이 끝난 키는 문·시동 거부(04)
  2. **차에서 반납하면 즉시 무효:** 반납 뒤 같은 키는 09로 거부
  3. **운행 중 재인증:** 시동 중 일정 시간마다 다시 인증. 실패하면 경고, **정차가 10분 이어지면 시동 해제**, 다시 시동은 07로 거부. 달리는 중에는 끄지 않는다(안전)
  4. **플래시 저장:** 배터리를 뽑았다 꽂아도 취소·반납·횟수·07 상태를 다시 읽는다
  5. **시계 되돌림 대응:** 차가 본 가장 늦은 시각을 저장. 시계를 5분 넘게 되돌리면 04로 거부
- 보안 기본: 서버가 서명한 키(HMAC-SHA256), 매번 새 난수(재전송 방지) → 자세한 내용은 5-1

### 5-1. 보안 구현 (기술요건 2)
- **(a) 암호 알고리즘 직접 구현 + 검증**
  - SHA-256과 HMAC-SHA256을 **라이브러리 없이 C로 직접 구현**했다(`firmware/stm32/Core/Src/sk_crypto.c`). mbedTLS·STM32 HASH 하드웨어를 쓰지 않는다
  - 표준 시험값과 비교: **FIPS 180-4 SHA-256 4개("abc", 2블록 메시지, 빈 문자열, "a" 100만 개), RFC 4231 HMAC Case 1~7 전부 일치** (PC 시험, `tests/test_vectors.c`)
  - 시험이 실제로 잡아내는지 확인: SHA-256 상수 하나만 바꾸면 23개가 FAIL로 잡힘 (PC 시험)
- **(b) 보안 기능이 있는 프로토콜 구현**
  - 인증 흐름: 앱 요청 → 차가 **16바이트 난수(하드웨어 난수기)** 발급 → 앱이 HMAC으로 답 → 차가 확인
  - 난수는 **1회용·5초 만료**: 재전송·만료는 02로 거부. 인증값이 틀리면 01로 거부
  - 인증값 비교는 **상수 시간 비교**(맞는 글자 수로 시간이 달라지지 않음)
  - 서버 동기화도 서명·난수·버전 역행 금지를 확인한 뒤에만 반영. 취소된 키는 동기화로 되살아나지 않는다
  - 실물: 변조·재전송·권한 초과·취소 키·옛 동기화 재전송 **각 100회, 잘못 허용 0** (Pi 5 경유, 11/28, 1회 실행)
- **구분해서 말할 것:** 차량(STM32)은 직접 구현이다. Python(서버·앱)은 표준 라이브러리 `hmac`을 쓰며, 서버의 서명 생성과 정답표(기준값) 생성용이다
- **한계:** 마스터키는 개발용 고정값(`00 01 … 1F`)이다. 실제 배포라면 차량마다 다른 키와 보호된 저장 영역이 필요하다

### 6. 실험 방법 — 같은 조건에서 방식 5개 비교
- 방식: A 서버 취소만 / B 기간 / C 횟수(N=2·4·8·16) / D 기간+횟수 / D-현실(기간 안 상한 + 유예, 후보 20개)
- 조건: 시드 고정 무작위 조건 표(상황 4종 × 30개, 본표는 상황마다 28개). **결과를 보기 전에 조건을 커밋**하고 바꾸지 않았다
- 평가 4축: ① 취소 뒤 얼마나 더 쓰나 ② 정상 이용자를 얼마나 막나 ③ 통신량 ④ 재부팅·시계 공격에 버티나
- 신뢰성: 같은 조건 대표 30개를 Python과 실제 C 판단 코드에 넣어 **30/30 같은 결과**(PC, 330번 시도 중 불일치 0)

### 10. 시연 (02 §9)
1. 등록 → 문 열기 → 자동 재잠금
2. 오프라인 → 취소 → A는 계속 열림 / C는 4번 뒤 05
3. 4번 다 쓴 뒤 보드 RESET → 재등록 → 여전히 05 (플래시)
4. 시동 → 오프라인 → 재인증 실패 경고 → USER 버튼으로 정차 → 30초(시연 설정) 뒤 시동 해제 → 다시 시동 07
5. B(기간) 보드 시연: 짧은 기간 키(예: 3분)로 만료 전 문 열림 → 만료 뒤 04 거부 (11/28 실물 30/30·30/30). 이어서 RTC 선을 빼면 04 → 시계 오류용 1회 키로 1번만 허용
- 예비 영상 12/4

### 11. 남은 틈 (숨기지 않는다)
- **기간 안 취소:** 결제 기간 중 서버에서만 취소된 키는 B가 막지 못한다(오프라인 시도 88번 허용, PC 모의). 차에서 반납하면 즉시 막힌다. 더 막으려면 D-현실처럼 정상 고객 거부가 늘어난다 → 운영사가 고를 몫, 우리는 근거를 준다
- **달리는 중에는 끄지 않는다** (안전 설계). 정차 전까지 운행 시간 상한은 없다
- **전원을 꺼 둔 시간**은 차가 알 수 없다 (시계 되돌림의 한계)
- **RTC를 일부러 끊으면:** 미리 받아 둔 시계 오류용 키로 1회까지 더 쓸 수 있다(키당 1회 상한). 원래 기간 키는 04로 막힌다
- **키 복사:** 키별 상한만 있다
- **수치의 성격:** 비교 수치는 PC 모의. 실물은 인증·취소 각 100회, 횟수 10라운드, 재부팅 50회(11/28, C 방식, 1회 실행), B 만료 직전·직후 각 30회(11/28, B 방식, 1회 실행). 통신량은 계산값

### 12. 쏘카에 제안한다면
- **정상 고객 불편 0%** (결제 기간 안 거부 0/127, PC 모의)
- **추가 비용이 작다:** 새 서버 없이 차량 단말의 판단 규칙으로 들어간다. 통신량은 키 1개일 때 2초에 232바이트(계산값)
- **근거가 있다:** 같은 조건 비교 실험, Python↔C 30/30, 보드 동작(실물 인증·취소 각 100회, 재부팅 50회)
- 업계 비교: INVERS·MoboKey·CCC도 기간 제한 키를 쓰지만, **취소된 키의 오프라인 사용량을 방식별로 비교한 공개 자료는 찾지 못했다** (00 §1.2, 11/27 조사)

### 13. 결론
> **"우리 모듈이 없으면 취소된 키로 차를 끌고 가도 차는 모른다. 우리 모듈이 있으면 기간이 끝난 키는 문과 시동이 거부되고, 끌고 가던 차는 정차 뒤 다시 출발하지 못하는 것이 목표다."**
- 향후: 서버가 서명한 시각을 동기화에 넣기(전원 꺼진 시간 문제), 실제 차 속도 센서로 정차 판단, 기간 안 취소를 정상 고객 불편 없이 줄이는 규칙
